# คู่มือทดสอบร่วม Mobile และ Web

**สำหรับ:** A (Web/Backend) และ B (Mobile) ทดสอบ flow ที่เริ่มจากฝั่งหนึ่งแล้วไปจบอีกฝั่ง
**จัดทำเมื่อ:** 12 ตุลาคม 2569
**อ้างอิงโค้ด:** `main` @ `d68e23f` (หลัง merge #277) ถ้า PR ที่ระบุในหัวข้อ 7 merge แล้ว ให้ทดสอบเพิ่มตามหัวข้อนั้น

เป้าหมายของคู่มือนี้คือยืนยันว่า **ข้อมูลที่ส่งจากมือถือไปถึงเว็บจริง และการตัดสินใจบนเว็บกลับไปถึงมือถือจริง** ผ่าน backend ตัวเดียวกัน ไม่ใช่แค่แต่ละฝั่งผ่านเทสของตัวเอง

---

## 1. หลักการสำคัญ

แอปมือถือและเว็บต้องต่อ **backend ตัวเดียวกัน** ซึ่งใช้ฐานข้อมูลเดียวกัน ถ้าต่างคนต่างรัน backend ในเครื่องตัวเอง สิ่งที่ B ส่งจากมือถือจะไปอยู่ในฐานข้อมูลของ B และจะไม่โผล่บนเว็บของ A

```
 มือถือ (B)  ──┐
               ├──>  Backend ตัวเดียว (port 3001)  ──>  PostgreSQL ตัวเดียว
 เว็บ (A)  ────┘
```

## 3. วิธีต่อมือถือเข้า backend ตัวเดียวกัน

เลือกแบบใดแบบหนึ่ง

### แบบ A: ใช้ backend ในเครื่องของ A, B ต่อผ่าน Wi-Fi (แนะนำ ถ้าข้อมูลตัวอย่างอยู่เครื่อง A)

ฝั่ง A
1. ต่อ Wi-Fi วงเดียวกับ B
2. หา IP ของเครื่อง: `ipconfig` แล้วดู `IPv4 Address` ของ Wi-Fi เช่น `192.168.1.25`
3. เปิด backend ตามหัวข้อ 2.2
4. อนุญาต port 3001 ใน Windows Firewall (ครั้งแรกที่ backend รันอาจมีหน้าต่างถาม ให้กด Allow บน Private network)
   ถ้าไม่มีหน้าต่างขึ้น ให้รันใน PowerShell แบบ Administrator:
   ```powershell
   New-NetFirewallRule -DisplayName "GPS backend 3001" -Direction Inbound -Protocol TCP -LocalPort 3001 -Action Allow -Profile Private
   ```
5. ส่ง IP ให้ B

ฝั่ง B
1. ทดสอบว่าต่อถึงก่อน: เปิด browser ในเครื่อง B ไปที่ `http://192.168.1.25:3001/api/v1/auth/login`
   ถ้าได้ข้อความ error ของ backend (เช่น 404 หรือ method not allowed) แปลว่าต่อถึงแล้ว ถ้าโหลดไม่ขึ้นเลย ให้ดูหัวข้อ 9
2. รันแอป:
   ```
   cd mobile
   flutter run --dart-define=API_BASE_URL=http://192.168.1.25:3001/api/v1 --dart-define=API_MOCK_MODE=false --dart-define=PUSH_NOTIFICATIONS_ENABLED=false
   ```

### แบบ B: รันทุกอย่างในเครื่องเดียว

ใช้ได้ถ้าเครื่องที่รัน backend มี Flutter และ Android Emulator อยู่แล้ว ไม่ต้องยุ่งกับ Wi-Fi หรือ Firewall
```
cd mobile
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:3001/api/v1 --dart-define=API_MOCK_MODE=false --dart-define=PUSH_NOTIFICATIONS_ENABLED=false
```
`10.0.2.2` คือที่อยู่ของเครื่อง host เมื่อมองจากใน Android Emulator (ใช้ `localhost` ไม่ได้)

### ทำไมต้องใส่ค่าทั้งสามตัว
| ค่า | เหตุผล |
|---|---|
| `API_BASE_URL` | ค่าเริ่มต้นคือ `localhost` ซึ่งใน emulator จะชี้ไปที่ตัว emulator เอง ไม่ใช่ backend |
| `API_MOCK_MODE=false` | ให้แอปเรียก backend จริง ไม่ใช้ข้อมูลจำลองในแอป |
| `PUSH_NOTIFICATIONS_ENABLED=false` | backend อยู่ในโหมด `NOTIFICATION_MODE=mock` อยู่แล้ว ไม่มี push จริงส่งมา และ Firebase ใน emulator อาจ error ตอน login |

## 5. ข้อควรรู้ระหว่างทดสอบ

- **เว็บดึงคิวรออนุมัติใหม่ทุก 20 วินาที** หลัง B ส่งคำขอ ให้รอสักครู่ หรือกดรีเฟรชหน้า
- **มือถือไม่ได้รับ push ที่เด้งขึ้นมา** (โหมด mock) แต่ backend ยังบันทึกการแจ้งเตือนลงฐานข้อมูลตามปกติ B ดูได้จากไอคอนกระดิ่ง "การแจ้งเตือน" ที่หน้าแรก (ต้องเปิดหน้าใหม่หรือดึงข้อมูลใหม่เอง)
- จดเวลาโดยประมาณของแต่ละขั้น ถ้าไม่ผ่านจะได้ไล่ดู log ของ backend และหน้า Audit Log ได้ตรงช่วง
- ทุก action ที่เปลี่ยนข้อมูลจะมีบันทึกในหน้า **Audit Log** ของเว็บ ใช้เป็นหลักฐานว่าคำขอจากมือถือมาถึง backend จริง

## 6. กรณีทดสอบ

แต่ละกรณีมี **ผู้ทำ** (A หรือ B) และ **ผลที่ต้องเห็น** ถ้าขั้นไหนไม่ตรง ให้หยุดแล้วจดในหัวข้อ 8 ก่อนไปขั้นถัดไป

### TC-01 ขอ Config Override จากมือถือ แล้วอนุมัติบนเว็บ

| # | ผู้ทำ | ขั้นตอน | ผลที่ต้องเห็น |
|---|---|---|---|
| 1 | B | หน้าแรก กด "ค้นหาอุปกรณ์" เลือกอุปกรณ์ที่ติดตั้งแล้ว | เปิดหน้า "รายละเอียดอุปกรณ์" |
| 2 | B | กด "Override ค่าพารามิเตอร์" แก้ค่า APN ใส่เหตุผล กด "ยืนยัน Override" | ส่งสำเร็จ ไม่มี error |
| 3 | A | เว็บ เมนู Approval Center | section "Per-device Config Override รออนุมัติ" มีคำขอใหม่ เห็นรหัสอุปกรณ์, ค่าที่ขอแก้ และเหตุผลตรงกับที่ B กรอก |
| 4 | A | กดอนุมัติ | คำขอหายจากคิว มีข้อความยืนยัน |
| 5 | B | หน้าแรก กดไอคอนกระดิ่ง "การแจ้งเตือน" | มีแจ้งเตือนว่าคำขอ Override ได้รับอนุมัติ (`config_override_approved`) ของอุปกรณ์เครื่องนั้น |
| 6 | A | เว็บ เมนู Audit Log | มีรายการ `device-config-override-request` (ผู้ทำ ST) และ `device-config-override-approve` (ผู้ทำ Operation) |

**ทำซ้ำแบบปฏิเสธ:** ขอใหม่อีกครั้ง แล้วให้ A กดปฏิเสธพร้อมเหตุผล B ต้องได้แจ้งเตือนว่าถูกปฏิเสธ (`config_override_rejected`)

หมายเหตุ: หน้ารายละเอียดอุปกรณ์บนมือถือไม่ได้แสดงสถานะคำขอ Config Override ให้ดูผลจากการแจ้งเตือนเท่านั้น

**ทดสอบสิทธิ์:** login มือถือด้วย `ot.test` แล้วเปิดหน้ารายละเอียดอุปกรณ์ ต้อง**ไม่เห็น**ปุ่ม "Override ค่าพารามิเตอร์" และ "ขอ Firmware Override" (ตามมติ #223 ST เท่านั้นที่ขอได้) และเว็บที่ login ด้วย `admin.test` ต้องไม่เห็น section Override ใน Approval Center

## 9. แก้ปัญหาที่เจอบ่อย

| อาการ | สาเหตุที่เป็นไปได้ | วิธีแก้ |
|---|---|---|
| มือถือ login ไม่ได้ ขึ้น connection error | `API_BASE_URL` ผิด หรือ Firewall บล็อก port 3001 | ลองเปิด URL ในหัวข้อ 3 แบบ A ข้อ 1 จาก browser ของเครื่อง B ก่อน แล้วเช็ค Firewall |
| มือถือใช้ได้ แต่ข้อมูลไม่ตรงกับเว็บ | ต่อ backend คนละตัว | เช็คว่า B ไม่ได้รัน backend ในเครื่องตัวเองพร้อมกัน และ `API_BASE_URL` ชี้ไปเครื่อง A |
| backend start ไม่ขึ้น ขึ้น TS error ว่า field ไม่มีใน type | Prisma Client ไม่ตรงกับ schema หลังสลับ branch | `cd backend && npx prisma generate` แล้วรันใหม่ |
| backend ขึ้น `EADDRINUSE :3001` | มี backend รันค้างอยู่แล้ว | ปิดตัวเก่าก่อน หรือใช้ตัวที่รันอยู่ |
| ส่งคำขอจากมือถือแล้ว เว็บไม่ขึ้น | รอไม่ถึง 20 วินาที | รอหรือรีเฟรชหน้า แล้วเช็ค Audit Log ว่าคำขอมาถึง backend หรือยัง |
| แอปค้างตอน login บน emulator | Firebase พยายามขอสิทธิ์ push | รันใหม่โดยใส่ `PUSH_NOTIFICATIONS_ENABLED=false` |
| เว็บหน้าใดหน้าหนึ่งพังทั้งหน้า | ข้อมูลมีสถานะที่เว็บยังไม่รู้จัก | จดชื่อหน้าและภาพ error แล้วแจ้ง A |
