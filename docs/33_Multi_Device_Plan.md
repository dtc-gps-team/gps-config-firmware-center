## 1. เป้าหมาย

1. กล่อง TA255 ใช้งานในระบบได้เหมือน BOX-0001 (ESP32): เห็นพิกัด ส่ง Config ผ่าน Task / คำขอหน้างาน / Campaign ได้
2. **ระบบจัดการเฉพาะค่าที่ตั้งเข้ากล่องผ่าน GPRS ได้จริงเท่านั้น** — ค่าที่ไม่มีคำสั่งไม่อยู่ในระบบ
3. กล่องรุ่นใหม่ในอนาคตเพิ่มเข้าระบบได้ **โดยไม่ต้องแก้ backend, Web, Mobile**
4. คนดูแลระบบมีเซอร์วิสเพิ่มแค่ **1 ตัว** (device-hub) ไม่ว่าจะมีกี่โปรโตคอล
5. ESP32 / Server กลางเดิม **ทำงานเหมือนเดิมทุกอย่าง**

### ไม่อยู่ในขอบเขต

- ค่าที่ตั้งได้แค่ผ่าน USB / Meitrack Manager (เช่น Fall Off interval, Exit G-fence interval) — **ไม่ใส่ในระบบ** ถ้าวันหนึ่งได้คำสั่ง GPRS มาค่อยเพิ่มตาม §5
- คำสั่งที่ไม่ใช่การตั้งค่า (ขอพิกัด, รีสตาร์ท, ล้างข้อมูล, คืนค่าโรงงาน) และคำสั่งอันตราย (เปลี่ยนเซิร์ฟเวอร์, ตัดน้ำมัน/รีเลย์) — ดู §5.3
- อัปเดต firmware TA255 ทางไกล — เอกสารไม่มีคำสั่งนี้
- เขียน firmware หรือแก้ Server กลาง ESP32 (`arduino_gps/`)
- แจ้งเตือนเหตุการณ์กล่องถึงคน — คงตาม docs/23 Q2

## 2. สภาพปัจจุบัน (เช็คจากโค้ด main `211f76a`)

### 2.1 ส่วนที่รองรับหลายรุ่นแล้ว

| ส่วน | หลักฐาน |
|---|---|
| ทะเบียนรุ่น | `model DeviceModel` เพิ่มรุ่นผ่านเว็บได้ |
| Campaign ผูกรุ่นเดียว | `Campaign.modelId` — CampaignService ตรวจตอนสร้าง/เพิ่มเครื่อง |
| Config ผูกรุ่น | `Config.modelId` (#481) |
| รายการค่าตั้งต่อรุ่น | `ConfigFieldDefinition` (ชื่อ field **ใช้ร่วมกันทุกรุ่น**) + `ConfigFieldDefinitionModelSupport` (field ไหนรองรับรุ่นไหน) |

→ การ "จำกัดให้ TA255 มีแค่ค่าที่ตั้งได้" ทำได้ด้วยของเดิม: ผูกเฉพาะ field ใน §5 กับรุ่น TA255 ไม่ต้องเพิ่ม schema

### 2.2 ส่วนที่ผูกกับ ESP32 / Server กลาง

**(ก) ทางส่งเข้ากล่องเลือกจาก env ตัวเดียวทั้งระบบ** — `DEVICE_CONFIG_APPLY_MODE` = `mock` | `real` | `central` ทุกเครื่องใช้ค่าเดียวกัน · จุดที่เช็คโหมดนี้ **23 จุด**: `device.service.ts` 14, `campaign-rollout.service.ts` 7, `config-apply-request.service.ts` 1, `config-applier.ts` 1

**(ข) ทุกการคุยกับกล่องผ่าน `CentralDeviceService` ตัวเดียว** — รอยต่อที่ดีอยู่แล้ว:

| method | ใครเรียก |
|---|---|
| `listDevices`, `getStatus` | central-device.controller (หน้า Device Search) |
| `findDevice` | device.service, config-apply-request.service, controller |
| `readReportedFields`, `readSupportedSchema`, `checkConfig` | device.service |
| `pushConfig`, `pushFirmware`, `findPreviousSuccessfulFirmwareVersion` | campaign-rollout.service |
| `getCommandOutcome` | central-rollout-poll.service (ถามผล + ลองใหม่อัตโนมัติ) |

ผลคำสั่งมีรูปกลางอยู่แล้ว: `pending` / `success` / `failed` / `skipped` / `unavailable` (`central-config.ts`)

**(ค) รับพิกัดได้แค่รูปแบบของ ESP32** — `POST /device-sync/:deviceId/telemetry/:key` · snake_case · event รู้จัก 3 ตัว · 1 request = 1 จุด · **จำกัด 60 ครั้ง/นาที/เครื่อง และ 300 ครั้ง/นาที/IP**

### 2.3 ปัญหาที่เจอระหว่างเช็คโค้ด

1. **field `protocol` ไม่ได้แปลว่า "ภาษาของกล่อง"** — ค่าที่ใช้จริงคือ `TCP` / `UDP` ระบบยังไม่มีที่บอกว่ารุ่นนี้ส่งผ่านทางไหน
2. **เพดาน 300 ครั้ง/นาที/IP จะชน device-hub** — hub ส่งพิกัดทุกกล่องจาก IP เดียว และ TA255 ส่งข้อมูลค้างย้อนหลังทีละหลายสิบชุด (ทดสอบเจอ 51 ชุด)
3. **Campaign ระบบของคำขอหน้างานรับทุกรุ่นปนกัน** (`modelId = null`) → ต้องเลือกทางส่ง **ต่อเครื่อง** ไม่ใช่ต่อ Campaign

## 3. ภาพรวมการออกแบบ

```
              ┌── CentralChannel ──► Server กลาง ESP32 (เดิม) ──► BOX-0001
backend ──────┤
  Router      ├── HubChannel ──────► device-hub (ใหม่ 1 เซอร์วิส) ──► TA255, รุ่นใหม่
  (ต่อเครื่อง)  │                        ├─ protocols/meitrack/
              │                        └─ protocols/<ใหม่>/
              └── Mock (dev/CI)

device-hub ──► POST telemetry เข้า backend
```

1. **backend เลือกทางส่งจากรุ่นของเครื่อง**
2. **backend ไม่รู้โปรโตคอลกล่อง** — รู้แค่ field กลาง device-hub แปลงเป็นคำสั่งเอง
3. **device-hub ตอบกลับในรูปเดียวกับ Server กลาง** — poll / ลองใหม่ / Auto Pause ใช้ต่อได้
4. **device-hub บอก backend ว่ารุ่นนี้ตั้ง field อะไรได้** (schema) — field ที่ไม่อยู่ใน schema ถูกปฏิเสธตั้งแต่ตอนทดสอบ Config ไม่ต้องรอถึงตอนส่ง

## 4. การตัดสินใจหลัก

### D1 — ระบุทางส่งที่รุ่น: `DeviceModel.deliveryChannel`

- เพิ่ม `deliveryChannel String?` ค่า `central` | `hub` | `none`
- **null = ใช้ env เดิม** → ข้อมูลเดิมทำงานเหมือนเดิม ไม่ต้อง backfill
- `none` = ใช้ระบบได้ แต่ปุ่ม "ส่งเข้ากล่อง" ปิดพร้อมเหตุผล
- ตั้งผ่านหน้าแก้ไขรุ่น (`PATCH /device-models/{id}`) · migration additive
- ไม่ใช้ field `protocol` เดิม เพราะความหมายคือ TCP/UDP

### D2 — รอยต่อเดียว: interface `DeviceChannel`

- interface ที่มี method ชุดเดียวกับ `CentralDeviceService` (§2.2ข)
- `CentralChannel` = ห่อของเดิม **ไม่เปลี่ยนพฤติกรรม** · `HubChannel` = HTTP client ไป device-hub
- `DeviceChannelRouter.forDevice(deviceId)` → ดูรุ่น → คืน channel
- แก้ 23 จุดจาก `mode === 'central'` เป็น "ถาม router" — ทยอยทีละ PR
- หน้า Device Search รวมรายการจากทุก channel

### D3 — device-hub ใช้ API รูปเดียวกับ Server กลาง

| device-hub API | เทียบกับ Server กลาง | ใช้ทำอะไร |
|---|---|---|
| `GET /devices` | `listGatewayDevices` | สถานะออนไลน์ + firmware ที่รายงาน |
| `GET /models/{model}/schema` | `getSchema` | **field ที่รุ่นนี้ตั้งได้จริง** + ชนิด + ช่วงค่า (จาก §5) |
| `PUT /devices/{id}/config` | `putDeviceConfig` | สั่งตั้งค่า → คืน `commandId` |
| `GET /commands/{id}` | `getCommand` | สถานะคำสั่ง |
| `GET /devices/{id}/config` | `getDeviceConfig` | ค่าที่อ่านกลับจากกล่องได้ (§5 คอลัมน์ "อ่านกลับ") + ค่าล่าสุดที่ตั้งสำเร็จ |
| `GET /devices/{id}/commands` | `listDeviceCommands` | ประวัติคำสั่ง |
| `POST /devices/{id}/firmware` | `pushFirmware` | TA255: ตอบ `rejected` "รุ่นนี้ไม่รองรับอัปเดตทางไกล" |

- auth ระหว่าง backend ↔ hub ด้วย token ผ่าน env · มี openapi ของ hub ใน repo
- field ที่ไม่อยู่ใน schema → `checkConfig` ตอบ `rejected` ตั้งแต่ตอนทดสอบ Config (กลไกเดียวกับที่ ESP32 ใช้อยู่)

### D4 — ยืนยันผล: ใช้วิธีที่ดีที่สุดที่คำสั่งนั้นมี

กล่องตอบ `OK` ไม่ได้แปลว่าค่าถูกใช้ (พิสูจน์แล้ววันที่ 17) แต่ละ field จึงมีระดับการยืนยัน:

| ระดับ | วิธี | field ที่ใช้ได้ |
|---|---|---|
| **อ่านกลับ** | ส่งคำสั่งเปล่า (เช่น `B14`) กล่องตอบค่าปัจจุบัน → เทียบกับที่ตั้ง | B14, B15, BBD, BC6 |
| **ดูจากพฤติกรรม** | ดูช่วงห่างรายงาน event 35 สองรอบติดกัน | A12 |
| **กล่องตอบรับ** | ได้ `OK` อย่างเดียว | ที่เหลือ |

สถานะใน hub `queued` → `sent` → `acked` → `verified` ส่งให้ backend ในรูปเดิม:

| ใน hub | backend เห็นเป็น | ข้อความ |
|---|---|---|
| `queued` / `sent` | `pending` | รอกล่องออนไลน์ / ส่งแล้ว รอกล่องตอบ |
| `acked` (field ที่ยืนยันต่อได้) | `pending` | กล่องตอบรับแล้ว กำลังยืนยัน |
| `verified` หรือ `acked` (field ที่ยืนยันได้แค่ตอบรับ) | `success` | ระบุใน detail ว่ายืนยันระดับไหน |
| อ่านกลับไม่ตรง / ยืนยันไม่ได้ในเวลาที่กำหนด | `failed` + `NOT_VERIFIED` | กล่องตอบรับแต่ค่าไม่ถูกใช้ |
| กล่องตอบ Error | `failed` + `DEVICE_REJECTED` | — |
| คิวหมดอายุ กล่องไม่เคยออนไลน์ | `skipped` | ตรงกับ `skipped_offline` เดิม |

- **ไม่เพิ่มสถานะใน backend** → poll, ลองใหม่, Auto Pause ใช้ของเดิม
- A12 ยืนยันไม่ได้ถ้ากล่องอยู่นอก geofence หรือถูกถอด (กล่องใช้รอบอื่นแทน) → `NOT_VERIFIED` พร้อมข้อความบอกสาเหตุที่เป็นไปได้

### D5 — คิวคำสั่งอยู่ใน device-hub

**คิวคืออะไร:** ESP32 ต่อสายกับ Server กลางตลอด สั่งเมื่อไรก็ได้ แต่ TA255 เป็นฝ่ายต่อเข้ามาเอง และหลุดได้ (ไม่มีสัญญาณ, ปิดเครื่อง, ต่อใหม่ทุก ~3 นาที) ถ้าสั่งตอนกล่องไม่อยู่ คำสั่งต้องรอในคิวก่อน แล้ว hub ส่งให้ทันทีที่กล่องต่อกลับมา

ตัวอย่าง: 09:00 Operation อนุมัติให้ตั้ง A12 → กล่องอยู่ในที่อับสัญญาณ → คำสั่งรอในคิว → 11:30 กล่องต่อกลับมา → hub ส่ง A12 → ยืนยันผล → `success`

- กล่องรับคำสั่งได้เฉพาะตอนต่อสายอยู่ → hub เก็บไว้ส่งตอนกล่องต่อเข้ามา
- **คำสั่งใหม่แทนที่คำสั่งเก่า**ของเครื่องเดียวกันที่ยังไม่ได้ส่ง (เก่า → `failed` + `SUPERSEDED`)
- **หมดอายุ** ค่าเริ่มต้น 24 ชม. → `skipped`
- คิวเก็บลงไฟล์ อยู่รอด hub restart
- ส่งทีละคำสั่งต่อเครื่อง รอคำตอบก่อนส่งตัวถัดไป · Config 1 ชุดที่มีหลาย field = หลายคำสั่ง → ผลรวมสำเร็จเมื่อทุกคำสั่งสำเร็จ · ถ้าบางตัวล้ม รายงานใน detail ว่าตัวไหน

### D6 — พิกัดจาก device-hub เข้า backend

**ระยะแรก (ไม่แก้ backend):** hub แปลงเป็นรูป `DeviceDataReportDto` แล้ว POST ทีละจุด · map event 19 → `OVERSPEED`, 20 → `GEOFENCE_ENTER`, 21 → `GEOFENCE_EXIT` · event อื่นส่งเป็น telemetry · key ต่อเครื่องเก็บใน config ของ hub · hub ชะลอเองไม่เกิน 60 ครั้ง/นาที/เครื่อง · รองรับได้ ~5 เครื่อง

**ระยะถัดไป (เมื่อกล่องเยอะ):** endpoint ใหม่สำหรับ hub ส่งหลายจุดใน request เดียว, auth ด้วย token ของ hub, เพดานแยก · เก็บ event code ดิบ (`DeviceEvent.eventType` เป็น string อยู่แล้ว) · endpoint เดิมของ ESP32 ไม่แตะ

### D7 — device-hub อยู่ใน repo นี้


- **hub ส่งได้เฉพาะคำสั่งใน `fields.js`** — ไม่มีช่องให้ส่งคำสั่งดิบจาก API · คำสั่งใน §5.3 ไม่มีทางถูกส่งจากระบบ

### D9 — ชื่อ field และ field หลายค่า

**ชื่อ field: ขึ้นต้นด้วยตระกูลโปรโตคอล เช่น `MEITRACK_TRACK_INTERVAL_SEC`**

| ทางเลือก | ปัญหา |
|---|---|
| ใช้ชื่อเดียวกับ ESP32 ถ้าความหมายตรงกัน | แก้ field ตัวหนึ่ง (หน่วย, ช่วงค่า, คำอธิบาย) กระทบทั้ง 2 รุ่น · หน่วยต่างกัน (A12 ทีละ 10 วิ) · ต้องไล่เทียบ schema ESP32 ทุกตัว |
| ตั้งชื่อกลางใหม่ไม่มี prefix | อาจชนชื่อ field ของ ESP32 ที่มีอยู่ (`fieldName` ห้ามซ้ำทั้งระบบ) |
| **prefix ตระกูลโปรโตคอล** ✅ | ไม่ชนแน่นอน · เห็นทันทีว่าเป็นของกล่องตระกูลไหน · Meitrack รุ่นอื่นใช้ field ชุดเดียวกันได้ |

ข้อเสียที่ยอมรับได้: ESP32 กับ TA255 ไม่มี field ร่วมกัน — ไม่กระทบเพราะ Campaign ผูกรุ่นเดียวอยู่แล้ว ไม่มีกรณีส่ง Config เดียวให้ 2 ยี่ห้อ

**field หลายค่า: แยกเป็นหลาย field ปกติ** (ไม่ใช้ field ชนิด `json`)

ตัวอย่าง B14 → `MEITRACK_IDLING_TIME_SEC`, `MEITRACK_IDLING_SPEED_KMH`, `MEITRACK_IDLING_ALERT_SEC`

| | แยกหลาย field ✅ | json field เดียว |
|---|---|---|
| หน้าสร้าง Config | ช่องกรอกปกติ มีหน่วย ช่วงค่า | กล่องข้อความ JSON ผู้ใช้พิมพ์ผิดง่าย |
| ตรวจช่วงค่า | ใช้ระบบเดิมได้ | ต้องเขียนตัวตรวจใหม่ |
| ช่างแก้ค่าเฉพาะเครื่อง (Override) | แก้ทีละค่าได้ | ต้องแก้ทั้งก้อน |
| หน้าเทียบค่า (diff) | เห็นว่าค่าไหนเปลี่ยน | เห็นแค่ก้อนเปลี่ยน |
| แก้ backend / Web / Mobile | ไม่ต้อง | ต้อง |

- `fields.js` ใน hub ระบุว่า field ไหนอยู่กลุ่มเดียวกัน → รวมเป็น 1 คำสั่ง
- Config ต้องมีครบทุก field ในกลุ่ม ไม่งั้น hub ปฏิเสธพร้อมบอกว่าขาดตัวไหน (ไม่เดาค่าเอง)

### 11.2 ทดสอบกับกล่อง TA255 จริง (วางบนโต๊ะ ต่อผ่าน pinggy)

| คำสั่ง | ระดับยืนยัน | ผล |
|---|---|---|
| B14 (idling) | อ่านกลับ | กล่องตอบ `180,5,120` ตรงกับค่าที่ตั้ง → สำเร็จ |
| B31 (LED) | ตอบรับ | ไฟ**สีน้ำเงิน**ดับ/กลับมากะพริบตามคำสั่ง · ไฟสีแดงไม่อยู่ใต้คำสั่งนี้ |
| A12 (รอบส่ง) | พฤติกรรม | 60 → 30 วิ ยืนยันจากเวลาแพ็กเก็ตจริง แล้วตั้งกลับ 60 วิ (วัดได้ 59 วิ) |
| พิกัด | — | เข้า backend ปกติ รวมข้อมูลที่กล่องเก็บค้างย้อนหลังตั้งแต่ 17 พ.ย. (800+ แถว) |

**ทดสอบเต็มขั้นตอนของระบบ** (ผ่าน API แบบเดียวกับที่เว็บ/แอปเรียก): สร้าง Config รอบส่ง 30 วิ → ทดสอบ → Operation อนุมัติ → ยืนยันติดตั้งเครื่อง → ช่างเปิด Task → ขอส่ง Config เข้าเครื่อง → Operation อีกคนอนุมัติ (Separation of Duty) → ปล่อย → backend → device-hub → กล่อง → **สำเร็จในประมาณ 70 วินาที**

**ทดสอบจากแอป Mobile จริง** (emulator ต่อ backend จริง, login เป็น ST): ค้นหาเครื่อง TA255 (แอปแสดงรุ่น TA255L, Firmware V028, ออนไลน์) → ขอส่ง Config รอบส่ง 30 วิ (แอปแสดง field `meitrack.track_interval_sec`) → ไม่แก้ค่าจึงอนุมัติทันที → กดส่งเข้ากล่อง → หน้าความคืบหน้าขึ้น "กล่องรับค่าใหม่แล้ว" ครบ 3 ขั้น **ใช้เวลา 1:09 นาที** · ไม่ได้แก้โค้ดแอปเลย

หลังทดสอบทั้ง 2 รอบตั้งกล่องกลับเป็นรอบส่ง 60 วิ

**ข้อสังเกตจากการต่อผ่าน pinggy:** กล่องหลุดทุก 3 นาที ครั้งละประมาณ 45 วินาที — กดส่งตอนกล่องหลุด ระบบไม่ส่งและแจ้ง "กล่องยังไม่ออนไลน์" (ถูกต้อง) กดใหม่ตอนกล่องกลับมาก็ผ่าน · ใช้งานจริงควรมีเซิร์ฟเวอร์ IP คงที่ (§12 ข้อ 3)

### 11.3 เจอระหว่างทดสอบและแก้แล้ว

- device-hub ฟังแค่ IPv4 → pinggy บน Windows ส่งต่อเข้า `::1` ไม่ได้ → แก้ให้รับทั้ง IPv4/IPv6
- นำเข้า field ต้องระบุ `--protocol TCP` (ค่าเริ่มต้นของสคริปต์เป็น HTTP) → เพิ่มใน README
- จาก code review ทั้ง branch แก้ 5 ข้อ: ยืนยันรอบส่งผิดตอนกล่องต่อสายใหม่, A12 รอบยาวทำคิวค้าง, hub ล่มเมื่อบันทึกคิวไม่ได้, hub ล่มทำให้สถานะ Server กลางบนเว็บผิด, กล่องหลัง CGNAT ถูกตัดตั้งแต่เครื่องที่ 6

### 11.4 ยังไม่ได้ทดสอบ (จาก §8)

## 12. เรื่องที่ขอให้พี่เลี้ยงตัดสินใจ
