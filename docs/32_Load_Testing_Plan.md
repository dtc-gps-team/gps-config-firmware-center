## 3. สิ่งที่เจอจากการอ่านโค้ดแล้ว (ก่อนรันทดสอบ)

### 3.1 ⚠️ ตัวลบข้อมูลเก่าตามไม่ทันตั้งแต่ 300 กล่อง

`purgeExpired()` (`backend/src/device-sync/device-telemetry.service.ts`) ลบ **สูงสุด 1,000 แถว × 50 รอบ = 50,000 แถว ต่อการรันหนึ่งครั้ง** และ job รัน **ชั่วโมงละครั้ง** (`device-telemetry-retention.job.ts`)

| | ข้อมูลเข้า / ชม. | ลบได้ / ชม. | ผล |
|---|---|---|---|
| จุดคุ้มทุน | 50,000 | 50,000 | ≈ **138 กล่อง** |
| 300 กล่อง | 108,000 | 50,000 | ค้างเพิ่ม ~58,000 แถว/ชม. → ฐานโตไม่หยุด |
| 3,000 กล่อง | 1,080,000 | 50,000 | ลบได้ไม่ถึง 5% ของที่เข้า |

ผล: เกิน ~138 กล่อง ข้อมูลเก่ากว่า 7 วันจะไม่ถูกลบหมด ฐานโตเรื่อยๆ จน disk เต็ม
→ ต้องแก้ก่อนขึ้นจริง (เช่น ลบตามช่วงเวลาแทนนับแถว, รันถี่ขึ้น, หรือแบ่งตาราง partition ตามวัน) — จะยืนยันด้วยการทดสอบ S5

### 3.2 ⚠️ เพดานต่อ IP อาจตัดข้อมูลกล่องจริงทิ้ง

`TelemetryRateLimitGuard` จำกัด **300 คำขอ/นาที ต่อ IP** (docs/23 §7.4) ถ้ากล่องใช้ซิมที่ผู้ให้บริการแปลง IP ร่วมกัน (CGNAT) หลายกล่องจะออกมาเป็น IP เดียว
กล่องส่งทุก 10 วิ = 6 คำขอ/นาที → **IP เดียวรับได้แค่ 50 กล่อง** (ถ้าส่งทุก 5 วิ เหลือ 25)
เกินนั้นได้ 429 และ **ข้อมูลหายถาวร** เพราะกล่องไม่ส่งซ้ำ (docs/23 §7.4)
→ ต้องเช็คกับพี่เลี้ยงว่าซิมของกล่องจริงออก IP แบบไหน แล้วตั้ง `TELEMETRY_RATE_LIMIT_PER_IP` ให้เหมาะ — จะยืนยันด้วย S7

### 3.3 จุดที่ต้องวัด ยังไม่รู้จากโค้ด

- telemetry 1 คำขอ = ค้นหาเครื่อง 1 ครั้ง (ตรวจ key) + insert 1 แถว (+ อัปเดตเวอร์ชัน firmware ถ้าส่งมา) → คอขวดน่าจะอยู่ที่ connection pool ของ Prisma กับการเขียนฐาน
- backend รัน instance เดียว ตัวนับ rate limit อยู่ในหน่วยความจำ

### 8.1 สิ่งที่ต้องแก้ก่อนขึ้น server จริง (เรียงตามความสำคัญ)

1. **ตัวลบข้อมูลเก่า (§3.1) — ต้องแก้** เกิน ~138 กล่อง ฐานโตไม่หยุดจน disk เต็ม · แนวทาง: ลบตามช่วงเวลาจนหมดในรอบเดียว (`DELETE ... WHERE "receivedAt" < cutoff` เป็นก้อนๆ จนไม่เหลือ) หรือรันถี่ขึ้น หรือ partition ตารางตามวันแล้ว drop ทั้ง partition
2. **เพดานต่อ IP (§3.2) — ต้องตัดสินใจ** ถ้าซิมกล่องออก IP ร่วม (CGNAT) เกิน 50 กล่อง/IP ข้อมูลหายครึ่งหนึ่ง · ถามพี่เลี้ยงเรื่องซิม แล้วยก `TELEMETRY_RATE_LIMIT_PER_IP` หรือพึ่ง limit ต่อเครื่องอย่างเดียว
3. **`GET /devices` ไม่แบ่งหน้า** ส่งทุกเครื่องทุกครั้ง (6,005 เครื่อง) ช้ากว่าหน้าอื่น ~10 เท่า และแย่ง CPU กับ telemetry · ต้องเพิ่ม pagination (backend + เว็บของ A + mobile)
4. **backend เป็น Node process เดียว** CPU เต็ม 1 core แล้วรับการเชื่อมต่อใหม่ไม่ทัน → connection refused = telemetry หายถาวร · บน server จริงควรรันหลาย instance (เช่น PM2 cluster) หรือแยกตัวรับ telemetry ออกจาก API หลัก

### 8.2 ข้อจำกัดของผลรอบนี้

- k6 กับ backend แย่ง CPU เครื่องเดียวกัน · Windows มีคิวรับการเชื่อมต่อเล็กกว่า Linux → ตัวเลขจุดพังเป็นค่าต่ำสุด
- ต้องรันชุดเดิมซ้ำบน server จริง (k6 รันจากอีกเครื่อง) ก่อนใช้ตัวเลขตัดสินใจเรื่องสเปก
