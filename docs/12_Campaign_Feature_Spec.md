# สเปคฟีเจอร์ Campaign — GPS Config & Firmware Center

> เอกสารนี้สรุปจากการคุยทบทวนความเข้าใจเรื่องฟีเจอร์ Campaign ระหว่างณัฐกับทีม (รวมทั้งจุดที่คุยกับแพรและพี่เลี้ยงแล้ว)
> เป้าหมายคือแก้ไขความเข้าใจเดิมที่คลาดเคลื่อน และวางขอบเขตให้ชัดก่อนนำไปพัฒนา/คุยกับอาจารย์
> อ้างอิงคู่กับ `GPS_Module_Ownership.md`, `docs/planning/02_GPS_Development_Plan.md` (Sprint Checklist) และ `CLAUDE.md`

---

## 1. ความเข้าใจเดิมที่ต้องแก้ไข

เอกสารแผนงานเดิม (Sprint Checklist แถวที่ 21-22) อธิบาย Campaign ว่าเป็นแค่ **"ปล่อยเวอร์ชัน Config/Firmware เป็นกลุ่ม (Pilot/Canary/Batch)"** และรวมขั้นตอน **"มอบหมายผู้รับผิดชอบหน้างาน"** ไว้ในตัวเดียวกัน

หลังทบทวนกับณัฐพบว่าความเข้าใจนี้ไม่ครบและมีจุดที่ผิด:

- ระบบเรา **ไม่มีหน้าที่มอบหมายงานให้ช่างหน้างานเลย** เพราะมีอีกระบบภายนอก (ที่พี่เลี้ยงเคยพูดถึง) ทำหน้าที่สั่งงานให้ช่างอยู่แล้ว ช่างรู้งานของตัวเองจากระบบนั้น — ระบบเราแค่ **ติดตามสถานะ** เท่านั้น (ดูรายละเอียดในหัวข้อ 5)
- Campaign มีขอบเขตกว้างกว่าที่เอกสารเดิมบอก คือมี **2 การใช้งาน** ไม่ใช่แค่ Pilot/Canary/Batch อย่างเดียว

---

## 2. ภาพรวม Campaign (นิยามใหม่)

Campaign คือกลไก **จัดกลุ่มอุปกรณ์ GPS** เพื่อใช้งาน 2 วัตถุประสงค์ ที่เป็นคนละหน้าจอ/เมนูกัน แต่ใช้แนวคิด "กลุ่มอุปกรณ์" ร่วมกัน:

| | Pilot/Canary/Batch Campaign | After-sales Campaign |
|---|---|---|
| **จุดประสงค์** | ทดสอบปล่อย Config/Firmware เวอร์ชันใหม่ทีละกลุ่มเล็กๆ ก่อนขยายเป็นวงกว้าง | รวมกลุ่มอุปกรณ์ที่มีปัญหา (จากทีมหลังการขายแจ้งมา) เพื่อตรวจสอบและแก้ไข |
| **ใครเริ่ม** | Operation (ตามแผนเดิม) | Operation / Admin / SuperAdmin / SW Engineer |
| **หน้าจอ** | แยกเมนูต่างหาก | แยกเมนูต่างหาก |
| **สถานะของ Campaign เอง** | มีจุดจบ (rollout สำเร็จ/ยกเลิก) | **ไม่มีสถานะปิด** — เป็นกลุ่มที่อยู่ถาวร ดูย้อนหลังได้ตลอด |

## 3. After-sales Campaign — รายละเอียด

### 3.1 การสร้างกลุ่ม

Operation/Admin/SuperAdmin/SW Engineer สร้างกลุ่มขึ้นเองหลังทีมหลังการขายแจ้งปัญหาเข้ามา จัดกลุ่มอุปกรณ์ได้แบบยืดหยุ่น เลือกเกณฑ์ผสมกันได้:

- ตามรุ่น/โมเดลอุปกรณ์ หรือเวอร์ชัน Firmware เดียวกัน
- เลือกเป็นรายเครื่องเอง (manual list)
- ตามพื้นที่/ลูกค้าเดียวกัน
- หรือผสมเกณฑ์ข้างต้นได้อิสระ

### 3.2 การวิเคราะห์ปัญหาในกลุ่ม

ตัวอย่าง: Campaign มีอุปกรณ์ 100 ตัว อาจพบว่ามีปัญหาจริงแค่ 25 ตัว ระบบต้องรายงานได้ว่าตัวไหนมีปัญหาและเพราะอะไร โดยได้ข้อมูลจาก **2 ทาง**:

1. **ระบบตรวจจับอัตโนมัติ** — เช่น เทียบเวอร์ชัน Config/Firmware ที่ควรมีกับที่อุปกรณ์ใช้จริง หรือดึงจากข้อมูล Incident ที่เชื่อมกับอุปกรณ์นั้น
2. **Operation พิมพ์เหตุผลเพิ่มเอง** (free text) — ในกรณีที่ระบบตรวจจับเองไม่ได้

### 3.3 สถานะรายเครื่อง

แต่ละเครื่องในกลุ่มมีสถานะของตัวเอง (เช่น "แก้แล้ว" / "ยังมีปัญหา") — ตัวกลุ่ม (Campaign) เองไม่มีสถานะปิด/จบงาน ใช้ติดตามสถานะของแต่ละเครื่องแทน

### 3.4 การอัปเดต Config เฉพาะเครื่องภายในกลุ่ม

กรณีลูกค้าหนึ่งรายในกลุ่มต้องการ Config เฉพาะของตัวเอง ระบบต้องอัปเดต Config ให้เฉพาะเครื่องนั้นได้ โดย **ไม่กระทบเครื่องอื่นในกลุ่มเดียวกัน**

**กลไกที่ตัดสินใจแล้ว:**

- ใช้กลไกเดียวกับฟีเจอร์ **Device Config Override** ที่มีอยู่แล้วในแผนเดิม (Sprint 3 แถวที่ 25) — ไม่ต้องสร้างฟีเจอร์ใหม่ซ้ำซ้อน
- ต้องผ่านขั้นตอนอนุมัติเหมือน Config ปกติทุกประการ ไม่มีทางลัด
- ต้องเก็บ**การเชื่อมโยงย้อนกลับ (traceability)** ไว้ว่า Config ที่ถูกแก้นี้เกี่ยวข้องกับ Campaign ไหน — เสนอให้เพิ่มคอลัมน์ nullable (เช่น `sourceCampaignId`) ในตาราง Config เมื่อไม่ได้มาจาก Campaign ก็ปล่อยว่างไว้ ไม่กระทบ flow ปกติของ Config Editor
- **หน้าตา UI** (จะเด้งไปหน้า Device Config Override เดิม หรือทำฟอร์มขึ้นในหน้า Campaign เลย) — ยังไม่ตัดสินใจ **รอแพร (A) เป็นคนตัดสินใจ**

> **หมายเหตุทางเทคนิค:** การต่อยอดนี้ไม่กระทบสถาปัตยกรรมเดิม เพราะเป็นการ "ต่อเติม" (เพิ่มฟิลด์ nullable + auto-fill ตอนเปิดจากหน้า Campaign) ไม่ใช่การเปลี่ยนแก้ของเดิม จุดเดียวที่ต้องระวังคือ `schema.prisma` เป็นไฟล์กลางที่แพรกับณัฐแก้ร่วมกัน ต้อง pull ก่อนแก้เสมอตามกฎใน `CLAUDE.md`

## 4. Pilot/Canary/Batch Campaign (ของเดิม — ยังอยู่ในขอบเขต)

ยังต้องคงไว้ตามแผนเดิม ทยอยปล่อย Config/Firmware เวอร์ชันใหม่ทีละกลุ่ม (เช่น กลุ่มทดสอบเล็กๆ ก่อน แล้วขยายเป็น Batch ใหญ่) เพื่อลดความเสี่ยงก่อนปล่อยทั้งหมด — เป็นคนละหน้าจอกับ After-sales Campaign ไม่ปนกัน

---

## 5. สิ่งที่ตัดออกจากแผนเดิม

**ขั้นตอน "มอบหมายผู้รับผิดชอบหน้างาน" ตัดออกจาก Campaign Wizard ทั้งหมด** เพราะระบบเราไม่มีหน้าที่สั่ง/มอบหมายงานให้ช่าง มีอีกระบบภายนอกทำหน้าที่นี้อยู่แล้ว (ปัจจุบันยังไม่เชื่อมต่อกัน ในอนาคตอาจพิจารณาเชื่อมต่อ)

สิ่งที่ระบบเรายังต้องมีคือหน้า **"ติดตามสถานะงาน" (Task Tracking)** เท่านั้น:

- เก็บสถานะปัจจุบัน + ประวัติการเปลี่ยนแปลงทั้งหมด (ใครเปลี่ยนสถานะอะไร เมื่อไหร่)
- อัปเดตสถานะได้ทั้งจากช่าง (มือถือ) และจาก Operation (เว็บ)
- ไม่มีหน้า "สร้างงาน/มอบหมายงาน" ในระบบเราเลย
