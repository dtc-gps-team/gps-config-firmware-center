# ข้อเสนอออกแบบ: ค่า Config เฉพาะเครื่องตอนเริ่ม Rollout

> เอกสารนี้เป็น**ข้อเสนอ ยังไม่ใช่มติ** เขียนให้ kittiphong (B) รีวิวก่อนลงมือทำ ตาม pattern เดียวกับ
> `docs/13` และ `docs/14` ยังไม่แก้ schema และยังไม่เขียนโค้ดใดๆ จนกว่า B เห็นด้วย
>
> **ที่มา:** รีวิวกับพี่เลี้ยง 12 ต.ค. 2569 ข้อ 3 ที่ว่า อุปกรณ์แต่ละเครื่องอาจมีบาง field ไม่เหมือนกัน
> แม้ใช้ Config แม่แบบเดียวกัน เช่น speed ปกติ 120 แต่เครื่องหนึ่งต้องเป็น 180 พี่เลี้ยงอยากให้แก้ค่า
> ทีละเครื่องได้ตอนเริ่ม Rollout ก่อนส่งเข้าขั้นตอนอนุมัติ
>
> **ส่วนของ R7** (Auto Pause แล้วสร้าง Incident) ไม่อยู่ในเอกสารนี้ เพราะผูกกับวิธีที่อุปกรณ์รายงานผลกลับ
> ซึ่งขึ้นกับข้อเสนอของ B เรื่องทดสอบด้วยโทรศัพท์ (R1) จะเขียนแยกหลังเห็นข้อเสนอนั้น

## 2. ระบบปัจจุบัน (เช็คกับโค้ดบน `main` แล้ว)

ระบบมีกลไกค่าเฉพาะเครื่องอยู่แล้ว คือ **Per-device Config Override** (issue #223) ใช้ตารางเดียวกันนี้ต่อได้
จึงสรุปกฎที่มีอยู่ก่อน เพราะข้อเสนอต้องอยู่ในกรอบเหล่านี้

| # | กฎของระบบเดิม | อยู่ที่ |
|---|---|---|
| 1 | `DeviceConfigOverride` ผูกกับ **`configId` ตัวใดตัวหนึ่ง** ตอน merge ค่าเข้าเครื่อง ระบบเลือกเฉพาะแถวที่ `configId` ตรงกับ Config ปัจจุบันของเครื่อง | `config-override-merge.ts` |
| 2 | merge ใช้แถว `approved` ที่ `versionNumber` มากสุดของ (เครื่อง, Config) แล้วเอา `fields` ทับ Config แม่แบบ | `mergeApprovedOverride()` |
| 3 | ทั้ง `apply-config` ของช่างและ Auto-apply ของ Rollout เรียก `mergeApprovedOverride()` ตัวเดียวกัน จึงได้ค่าเดียวกันเสมอ | `device.service.ts`, `campaign-rollout.service.ts` |
| 4 | `fields` ในแถว override **สะสม**: แถวใหม่ = ค่าที่ approved ล่าสุดของ (เครื่อง, Config นั้น) บวกค่าที่ขอใหม่ | `overrideDeviceConfig()` |
| 5 | `versionNumber` นับต่อเครื่อง **รวมทุก Config** (ล่าสุด + 1) และ unique ที่ (deviceId, versionNumber) | schema `DeviceConfigOverride` |
| 6 | (เครื่อง, Config) หนึ่งคู่มีคำขอ `pending` ได้ทีละ 1 รายการ ซ้อนไม่ได้ (409) | `overrideDeviceConfig()` |
| 7 | field ที่ override ได้ต้อง `stOverridable = true`, รองรับโมเดล/โปรโตคอลนั้น, ชนิดข้อมูลถูก และอยู่ใน `allowedValues` ถ้ากำหนดไว้ | `validateOverridableFields()` |
| 8 | ปัจจุบันมีแค่ ST ขอจากมือถือ และ Operation อนุมัติแยกทีละคำขอ | #223, #225, #226 |

**ข้อ 1 คือประเด็นหลักของเอกสารนี้:** เมื่อเปลี่ยนไปใช้ Config แม่แบบตัวใหม่ ค่าเฉพาะเครื่องเดิมจะ**ไม่ตามไป
อัตโนมัติ** (ถูกต้องแล้ว เคยแก้บั๊กนี้ใน #225 เพราะต่างโมเดลจะได้ field ที่ไม่ผ่านการตรวจติดมาด้วย) ดังนั้น
แบบ ค. ต้องมีกลไก "ยกค่าเดิมมาใส่ Config ใหม่" ที่ชัดเจน ไม่ใช่แค่หน้าจอเตือน

## 3. ข้อเสนอ

### 3.1 ภาพรวมของ flow

```
Operation เปิดหน้าเริ่ม Rollout
   |
   | 1. เลือก Config แม่แบบ (และเครื่องที่ไม่เข้ากันถูกปิดไว้แล้วตาม #288)
   | 2. ระบบดึง "ค่าพิเศษเดิม" ของแต่ละเครื่องมาเป็นตัวเลือก (แบบ ค.)
   | 3. Operation เลือกต่อเครื่อง: ใช้ค่าพิเศษเดิมต่อ / ใช้ตามแม่แบบใหม่ / แก้ค่าเอง
   | 4. กรอกเหตุผล แล้วกดเริ่ม Rollout
   v
Rollout สถานะ pending_approval  (ค่าเฉพาะเครื่องเก็บไว้ที่ target ยังไม่มีผลกับเครื่องไหน)
   |
   | 5. Operation อีกคนเปิดหน้ารายละเอียดอนุมัติ (R4) เห็นค่าที่ต่างจากแม่แบบ แล้วอนุมัติ
   v
Rollout approved
   |
   | 6. Operation กด "ปล่อยเข้าอุปกรณ์"
   |    ในทรานแซกชันเดียวกับการเปลี่ยนสถานะเป็น active:
   |    บันทึกค่าเฉพาะเครื่องเป็น DeviceConfigOverride สถานะ approved
   v
Auto-apply เรียก mergeApprovedOverride() ตามเดิม ได้ค่ารวมโดยไม่ต้องแก้ตัว apply
```

### 3.2 จุดตัดสินใจหลัก 1: เก็บค่าที่ผู้ใช้กรอกไว้ที่ไหนระหว่างรออนุมัติ

| ทางเลือก | ทำยังไง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **ก. คอลัมน์ใหม่ที่ target (เสนอ)** | เพิ่ม `proposedFields Json?` ใน `CampaignRolloutTarget` ค่าอยู่กับ Rollout จนกว่าจะปล่อย แล้วค่อยบันทึกเป็น override | ค่าอยู่ที่เดียวกับ Rollout ไม่รบกวนคิว Override ของช่าง ปฏิเสธ Rollout แล้วไม่มีอะไรต้องล้าง | เพิ่มคอลัมน์ใน schema ร่วม (additive) |
| ข. สร้างแถว `DeviceConfigOverride` สถานะ `pending` ตอนเริ่ม Rollout | ใช้ตารางเดิมตรงๆ | ไม่ต้องเพิ่มคอลัมน์ | ไปโผล่ในคิว Override ของ Approval Center ทำให้ต้องอนุมัติสองที่ และชนกฎข้อ 6 (ช่างขอซ้อนไม่ได้) ต้องมี logic แยกว่าแถวไหนมาจาก Rollout |
| ค. ไม่เก็บเป็น override เลย ให้ Auto-apply รวมค่าจาก target โดยตรง | เพิ่ม logic ใน `autoApplyConfig()` | ไม่แตะตาราง override | ค่าไม่ถูกจำไว้กับเครื่อง ทำแบบ ค. ไม่ได้ และ apply-config ของช่าง/อุปกรณ์ดึงเอง (R1) จะไม่เห็นค่านี้ |

**เสนอทางเลือก ก.**

### 3.3 จุดตัดสินใจหลัก 2: บันทึกเป็น override ตอนไหน (อนุมัติ หรือ ปล่อย)

| ทางเลือก | ปัญหา |
|---|---|
| ตอนอนุมัติ | `reject()` รับสถานะ `approved` ด้วย (ถอยก่อนปล่อย ตั้งแต่ #250) ถ้าอนุมัติแล้วบันทึกค่าไปแล้วค่อยปฏิเสธ จะมีแถว `approved` ค้างเป็นค่าที่ไม่เคยถูกใช้จริง ต้องมีโค้ดย้อนกลับ |
| **ตอนปล่อย (เสนอ)** | บันทึกในทรานแซกชันเดียวกับ `updateMany` ที่เปลี่ยน `approved` เป็น `active` ซึ่งมีตัวกันกดซ้ำอยู่แล้ว (มีแค่ผู้ชนะที่บันทึก) ไม่มีอะไรต้องย้อนกลับ ค่าที่ถูกบันทึกคือค่าที่ถูกนำไปใช้จริงเท่านั้น |

ค่า `proposedFields` แก้ไม่ได้หลังสร้าง Rollout (ไม่มี endpoint แก้) สิ่งที่ผู้อนุมัติเห็นจึงเป็นสิ่งเดียวกับ
ที่ถูกบันทึกตอนปล่อย

**วิธีบันทึกแต่ละแถว** (ใช้กฎเดิมข้อ 4 และ 5):
- `configId` = Config ของ Rollout นี้
- `fields` = ค่า approved ล่าสุดของ (เครื่อง, Config นี้) ถ้ามี บวก `proposedFields`
- `versionNumber` = ล่าสุดของเครื่อง + 1 (อ่านในทรานแซกชันเดียวกัน ดักชน P2002 เหมือน `overrideDeviceConfig()`)
- `overriddenBy` = ผู้สร้าง Rollout, `decidedBy` = ผู้อนุมัติ Rollout, `decidedAt` = เวลาที่อนุมัติ, `status` = `approved`
- `reason` = เหตุผลที่ผู้สร้างกรอกตอนเริ่ม Rollout

### 3.4 จุดตัดสินใจหลัก 3: field ไหนที่ Operation แก้ได้

กฎเดิมข้อ 7 ใช้ธง `stOverridable` ซึ่งตั้งไว้สำหรับช่างหน้างาน ตัวอย่างของพี่เลี้ยง (speed) อาจไม่ใช่
field ที่เปิดให้ช่างแก้ ทางเลือก:

| ทางเลือก | ผล |
|---|---|
| ก. ใช้ `stOverridable` เหมือนเดิม | Operation แก้ได้เท่ากับช่าง ถ้า speed ไม่ได้เปิดไว้ก็แก้ไม่ได้ ต้องไปเปิดธงในคลัง Parameter ก่อน ซึ่งเปิดให้ช่างแก้ด้วย |
| **ข. Operation แก้ได้ทุก field ที่โมเดล/โปรโตคอลนั้นรองรับ (เสนอ)** | ตรวจชนิดข้อมูลและ `allowedValues` เหมือนเดิม แต่ไม่ต้องมี `stOverridable` เพราะมีการอนุมัติโดยอีกคนอยู่แล้ว field ที่มีธง `sensitive` หรือ `restartRequired` แสดงเครื่องหมายเตือนในแผงแก้ค่า และขึ้นเป็นกลุ่มแรกในหน้าอนุมัติ |
| ค. เพิ่มธงใหม่ เช่น `operationOverridable` | ควบคุมละเอียดที่สุด แต่เพิ่ม field ในคลัง Parameter ต้องไล่ตั้งค่าให้ทุกตัว |

**เสนอทางเลือก ข.** เป็นฟังก์ชันตรวจใหม่แยกจาก `validateOverridableFields()` (ใช้ `matchesDataType` ตัวเดิม)
ไม่แก้ฟังก์ชันเดิมที่ช่างใช้อยู่

### 3.5 แบบ ค.: ค่าพิเศษเดิมตามไปยังไง

**แหล่งของ "ค่าพิเศษเดิม":** แถว `DeviceConfigOverride` สถานะ `approved` ที่ `versionNumber` มากสุดของเครื่องนั้น
ไม่สนว่าผูกกับ Config ตัวไหน (ค่าสะสมของ Config นั้นอยู่ใน `fields` ของแถวเดียวอยู่แล้ว)

**ขั้นตอน**
1. ผู้ใช้เลือก Config แม่แบบ ระบบถามข้อมูลของเครื่องในกลุ่ม (endpoint ใหม่ ดูข้อ 3.6)
2. ระบบคืนต่อเครื่อง: ค่าพิเศษเดิม, มาจาก Config ตัวไหน, ใครเป็นคนตั้ง และ field ไหนที่ **Config ใหม่ไม่รองรับ**
   (ถูกตัดทิ้งพร้อมเหตุผล)
3. หน้าจอแสดงต่อเครื่องที่มีค่าพิเศษเดิม ให้เลือก **ใช้ค่าพิเศษเดิมต่อ** หรือ **ใช้ตามแม่แบบใหม่**
   ปุ่มเริ่ม Rollout กดไม่ได้จนกว่าจะเลือกครบทุกเครื่องที่มีตัวเลือก
4. สิ่งที่ส่งไป backend คือ**ค่าสุดท้ายที่เลือกแล้ว** (`deviceValues`) ฝั่ง backend ไม่เติมค่าให้เอง จึงไม่มีค่าไหน
   เปลี่ยนเงียบๆ จากฝั่งเซิร์ฟเวอร์

**คำถามเปิดที่เกี่ยวข้อง:** ค่าพิเศษที่ช่างขอและ Operation อนุมัติไว้ (#223) ควรถูกนับเป็น "ค่าพิเศษเดิม" ด้วยไหม
เสนอว่านับ เพราะเป็นค่าที่อยู่บนเครื่องจริงตอนนี้ และหน้าจอแสดงที่มา (ช่างขอ หรือตั้งตอน Rollout) ให้ผู้ใช้เห็น

### 3.6 API ที่ต้องเพิ่มและแก้

**แก้ `POST /campaigns/{campaignId}/rollouts`** (additive ไม่กระทบผู้เรียกเดิม)

```json
{
  "payloadType": "Config",
  "configId": "…",
  "excludeDeviceIds": ["DEV-0301"],
  "deviceValues": [
    { "deviceId": "DEV-0105", "fields": { "SPEED_LIMIT": 180 } }
  ],
  "deviceValuesReason": "รถคันนี้ใช้กับงานทางไกล ลูกค้าขอเพดานความเร็วสูงกว่าปกติ"
}
```

กฎการตรวจ (ตอบ 400 พร้อมรายการ error ต่อ field):
- ใช้ได้เฉพาะ `payloadType = Config`
- `deviceId` ต้องเป็นเครื่องที่อยู่ใน Rollout จริง (ไม่ถูกเอาออก ไม่ใช่เครื่องที่ไม่เข้ากัน)
- ตรวจชนิดข้อมูล, `allowedValues`, และรองรับโมเดล/โปรโตคอลตามข้อ 3.4
- ต้องมี `deviceValuesReason` ถ้ามี `deviceValues`
- ถ้า (เครื่อง, Config นี้) มีคำขอ override `pending` ของช่างค้างอยู่ ตอบ 409 พร้อมชื่อเครื่อง ให้ตัดสินใจคำขอนั้น
  ก่อน (เหตุผลดูข้อ 5)

**เพิ่ม `GET /campaigns/{campaignId}/rollouts/device-values?configId=…`** (อ่านอย่างเดียว) ใช้ข้อ 3.5

**แก้ response ของ Rollout และ target:** target เพิ่ม `proposedFields` (nullable) ให้หน้ารายละเอียดอนุมัติ
(R4) แสดงได้ ค่าที่ `sensitive` ถูก mask ฝั่ง backend ก่อนส่ง เหมือนที่ Approval Center ทำกับคำขอ Override

**ไม่ต้องเพิ่มสิทธิ์ใหม่:** ใช้ resource และ action ของ Campaign Rollout เดิมทั้งหมด

### 3.7 Schema

เพิ่มหนึ่งคอลัมน์ (additive ไม่แก้ migration เดิม):

```prisma
model CampaignRolloutTarget {
  // ...
  /// ค่าเฉพาะเครื่องที่ Operation เสนอไว้ตอนเริ่ม Rollout (ยังไม่มีผลกับเครื่อง)
  /// บันทึกเป็น DeviceConfigOverride ตอน release() เท่านั้น ดู docs/17
  proposedFields Json?
}
```

เป็นการเพิ่มของโปรเจกต์เอง ไม่มีใน Data Dictionary จึงต้องมี comment อธิบายเหนือ field ตามกฎใน CLAUDE.md
ก่อนแก้ต้อง `git pull origin main` เพราะ `schema.prisma` เป็นไฟล์ร่วม

## 5. กรณีขอบที่ต้องรองรับ

| กรณี | ทำยังไง |
|---|---|
| ช่างขอ override ค้างอยู่ (pending) ของ (เครื่อง, Config นี้) | บล็อกตอนสร้าง Rollout ด้วย 409 เหตุผล: ถ้าปล่อยผ่านแล้วบันทึกแถวใหม่ที่ `versionNumber` สูงกว่า แล้วต่อมาช่างคนนั้นได้รับอนุมัติ แถวที่อนุมัติทีหลังมี `versionNumber` ต่ำกว่าจะถูก `mergeApprovedOverride()` ข้ามเงียบๆ |
| Rollout ถูกปฏิเสธ (ทั้งก่อนและหลังอนุมัติ) | ไม่มีอะไรต้องล้าง เพราะค่ายังอยู่ที่ target ยังไม่ถูกบันทึกเป็น override |
| กดปล่อยซ้ำ / สองคนกดพร้อมกัน | ตัวกัน `updateMany` เดิมของ `release()` ยังเป็นตัวตัดสิน ผู้ชนะเท่านั้นที่บันทึก override |
| Resume หลัง Auto Pause | ไม่บันทึกซ้ำ เพราะการบันทึกอยู่ใน `release()` ครั้งเดียว |
| เครื่องเดียวกันอยู่ใน Rollout สองกลุ่ม | กลุ่มหนึ่งรันได้ทีละรอบอยู่แล้ว ส่วนข้ามกลุ่มใช้กฎ `versionNumber` ล่าสุดชนะตามเดิม |
| ผู้ใช้กรอกค่าแล้วเอาเครื่องนั้นออกจากรอบ | ฝั่งเว็บทิ้งค่าของเครื่องที่ถูกเอาออก ฝั่ง backend ปฏิเสธ `deviceValues` ของเครื่องที่ไม่อยู่ในรอบ (400) |
| กลุ่มใหญ่ (หลายร้อยเครื่อง) | จำกัดจำนวนเครื่องที่มี `deviceValues` ต่อ Rollout (เสนอ 200) รอบแรกยังไม่มีการตั้งค่าเดียวกันให้หลายเครื่องพร้อมกัน ดูข้อ 7 |

## 7. คำถามเปิด (ขอให้ B ช่วยตัดสิน)

1. **จุดตัดสินใจ 3.2:** เห็นด้วยกับคอลัมน์ใหม่ที่ target (ทางเลือก ก) ไหม
2. **จุดตัดสินใจ 3.3:** บันทึกเป็น override ตอนปล่อย ไม่ใช่ตอนอนุมัติ เห็นด้วยไหม
3. **จุดตัดสินใจ 3.4:** Operation แก้ได้ทุก field ที่โมเดลรองรับ (ทางเลือก ข) หรืออยากคงธง `stOverridable`
4. **ค่าพิเศษที่ช่างขอ** นับเป็น "ค่าพิเศษเดิม" ในแบบ ค. ด้วยไหม
5. **เหตุผล:** หนึ่งเหตุผลต่อทั้ง Rollout พอไหม หรืออยากให้ระบุต่อเครื่อง
6. **R1:** ฝั่งที่ให้ค่าแก่อุปกรณ์จะเรียก `mergeApprovedOverride()` ตัวเดียวกันได้ไหม
7. **Mobile:** ข้อความที่เกี่ยวกับ `hasDeviceOverride` ในแอปต้องปรับไหม
8. **รอบถัดไป (ไม่อยู่ใน PR แรก):** ตั้งค่าเดียวกันให้หลายเครื่องพร้อมกัน เช่น เลือก 30 เครื่อง แล้วตั้ง SPEED_LIMIT
   เป็นค่าเดียวกัน ซึ่งจะสำคัญมากเมื่อมีรถหลายร้อยคัน ทำเป็นรอบหลังได้ไหม
