## 3. หลักการ

- **`mock` (ค่าเริ่มต้น ไม่เปลี่ยน):** ทำงานเหมือนเดิมทุกอย่าง ปล่อย Rollout แล้ว backend apply ให้ทุกเครื่องทันที
  เดโมและเทสต์เดิมไม่กระทบ
- **`real`:** ปล่อย Rollout แล้ว backend **ไม่** apply เอง เครื่องเป้าหมายค้างเป็น `pending` จนกว่าเครื่องจะ
  มาดึงงานและรายงานผลเอง
- **โหมดถูกบันทึกไว้ที่ Rollout ตอนปล่อย** (`CampaignRollout.applyMode`) ไม่อ่าน env ใหม่ทุกครั้ง เหตุผล: ถ้าเปลี่ยน env
  กลับเป็น `mock` หลังทดสอบ Rollout ที่ปล่อยไปตอน `real` ยังต้องรอเครื่องและหมดเวลาได้ตามปกติ ไม่ค้างตลอดไป
  และหน้าเว็บบอกได้ว่า Rollout นั้นรอเครื่องจริงหรือไม่ Rollback และ Resume ใช้โหมดของ Rollout ต้นเรื่อง
- Auto Pause, Resume และการนับผล ใช้กลไกเดิมทั้งหมด
- Rollback ในโหมด `real` ต้องปรับ 1 จุด ดูหัวข้อ 3.1
- Rollback ของ Firmware (สลับพาร์ทิชัน) ยังเป็น mock แยกต่างหาก ไม่อยู่ในขอบเขตนี้

### 3.1 Rollback ในโหมด `real`

ตอนนี้ Rollback ทำ 2 อย่าง: เปลี่ยน Rollout เดิมเป็น `cancelled` พร้อมเปลี่ยนเครื่องที่ยัง `pending` เป็น `failed`
และสร้าง Rollout ใหม่ส่ง Config เก่า**เฉพาะเครื่องที่สำเร็จ** เพราะในโหมด `mock` เครื่องที่ยัง `pending` คือเครื่องที่ยัง
ไม่ได้รับอะไรเลย

ในโหมด `real` ไม่จริงแล้ว เครื่องที่**ดึงงานไปแล้วแต่ยังไม่รายงานผล** (Applying) อาจใช้ Config ที่มีปัญหาไปแล้ว ถ้าไม่รวม
เข้า Rollback เครื่องนั้นจะค้างกับ Config ที่มีปัญหาโดยไม่มีใครรู้

**เสนอ:** Rollback ในโหมด `real` ส่ง Config เก่าให้เครื่องที่ **สำเร็จ หรือ ดึงไปแล้ว (`pulledAt` ไม่ว่าง)** ส่วนเครื่องที่
ยังไม่ได้ดึงไม่ต้องส่ง เพราะยังใช้ Config เก่าอยู่แล้ว

## 4. Endpoint ที่อุปกรณ์เรียก

ยืนยันตัวตนด้วย header `X-Device-Api-Key` ผ่าน `DeviceApiKeyGuard` (ไม่ใช่ JWT เพราะอุปกรณ์ไม่ใช่ผู้ใช้)

- openapi เพิ่ม security scheme ใหม่ `deviceApiKey` (apiKey ใน header) ใช้กับ 2 endpoint นี้แทน `bearerAuth`
- ไม่ผ่าน `PermissionGuard` และไม่อยู่ในตารางสิทธิ์ตาม role ของ `RBAC_Matrix.md` เพราะไม่มี role แต่จะบันทึกใน
  changelog ของ RBAC_Matrix ว่ามี actor ชนิดอุปกรณ์เพิ่ม
- `deviceId` ใน path ต้องตรงกับ key (guard ตรวจอยู่แล้ว) เครื่องหนึ่งดึงหรือรายงานงานของอีกเครื่องไม่ได้

**เรื่อง path:** `docs/14` เคยร่างไว้เป็น `GET /devices/{deviceId}/config` แต่ path นี้ถูกใช้แล้วโดย endpoint ของ
staff (`getCurrentConfig` ที่ใช้ JWT) จึงเสนอ prefix ใหม่ `/device-sync/` แยกให้ชัดว่าเป็นของอุปกรณ์

### 4.1 `GET /device-sync/{deviceId}/jobs` ดึงงานที่รออยู่

```json
{
  "serverTime": "2026-10-20T10:00:00Z",
  "pollAfterSeconds": 30,
  "jobs": [
    {
      "jobId": "id ของ CampaignRolloutTarget",
      "rolloutId": "...",
      "createdAt": "2026-10-20T09:58:00Z",
      "payloadType": "Config",
      "config": {
        "configId": "...",
        "name": "GT06N มาตรฐาน",
        "deviceModel": "GT06N",
        "protocol": "TCP",
        "fields": { "SPEED_LIMIT": 180, "APN": "internet" }
      }
    }
  ]
}
```

**งานที่ส่งให้เครื่อง**
- งานของ Rollout ที่ `applyMode = real`, สถานะ `active` และ target ยัง `pending`
- งานที่ถูก "ข้าม: เครื่องออฟไลน์" ตามเงื่อนไขในหัวข้อ 16.4
- **ไม่ส่ง** งานของ Rollout ที่ `paused`, `cancelled` หรือ `completed` (ยกเว้นข้อบน) นี่คือสิ่งที่ทำให้ Auto Pause หยุดเครื่อง
  ที่ยังไม่ได้ดึงได้จริง

**รายละเอียดอื่น**
- เรียงตาม `createdAt` จากเก่าไปใหม่ **เครื่องต้องทำทีละงานตามลำดับ** งานสุดท้ายคือค่าที่ใช้จริง (กรณีเครื่องอยู่ใน 2
  Rollout ที่ active พร้อมกัน)
- `fields` คือค่าหลัง `mergeApprovedOverride()` **ณ เวลาที่ดึง** ค่าที่ sensitive ส่งค่าจริง เพราะเครื่องต้องใช้งาน
- **ตรวจ Config ซ้ำก่อนส่งทุกครั้ง** ถ้า Config ถูกลบหรือไม่อยู่ในสถานะที่ใช้ได้แล้ว ไม่ส่งงานนั้น และเปลี่ยน target เป็น
  `failed` พร้อมเหตุผล (เงื่อนไขเดียวกับที่ `autoApplyConfig()` ตรวจในโหมด `mock`)
- ครั้งแรกที่งานถูกส่ง บันทึก `pulledAt` ที่ target หน้าเว็บจึงแยกได้ว่า Waiting (ยังไม่มาดึง) หรือ Applying (ดึงไปแล้ว
  รอผล) ส่งซ้ำได้ถ้าเครื่องดึงอีกก่อนรายงานผล แต่ `pulledAt` คงเวลาครั้งแรก
- ไม่มีงาน คืน `"jobs": []` (200) ไม่ใช่ 404
- `serverTime` ให้เครื่องใช้ดูเวลาที่ถูกต้อง (นาฬิกาในกล่องอาจคลาด) ไม่บังคับใช้

### 4.2 `POST /device-sync/{deviceId}/jobs/{jobId}/result` รายงานผล

```json
{ "result": "success", "detail": "ข้อความจากเครื่อง (ไม่บังคับ ไม่เกิน 500 ตัวอักษร)" }
```

ตอบกลับ:
```json
{ "accepted": true }
{ "accepted": false, "reason": "already-reported" }
```

| สถานะของงานตอนรายงาน | ผล | `reason` |
|---|---|---|
| `pending` ใน Rollout ที่ `active` หรือ `paused` | บันทึกผลผ่าน `recordTargetResult()` | (accepted) |
| `skipped_offline` (หัวข้อ 16.4) | บันทึกผลแบบล่าช้า | (accepted) |
| มีผลไปแล้ว | ไม่เปลี่ยน เก็บข้อความไว้ให้ Operation เห็น | `already-reported` |
| Rollout ถูก Rollback (`cancelled`) | ไม่เปลี่ยน เก็บข้อความไว้ | `rollout-closed` |

- **ส่งซ้ำได้ (idempotent):** ทุกกรณีที่ไม่บันทึกตอบ 200 ไม่ใช่ error เครื่องจะได้หยุดส่งซ้ำ (มือถือเน็ตหลุดแล้วส่งซ้ำเป็น
  เรื่องปกติ)
- รายงานผลโดยไม่เคยดึงงาน: รับได้ และตั้ง `pulledAt` เป็นเวลาที่รายงาน
- `recordTargetResult()` ใช้ `rolloutId` ของ job นั้นตรงๆ ไม่เปิด fallback แบบ path ของ Mobile
- `jobId` ที่ไม่ใช่ของเครื่องนี้ หรือไม่มีอยู่ ตอบ 404 (pattern เดียวกับ IDOR Prevention ใน CLAUDE.md)
- body ผิดรูปแบบ ตอบ 400, key ผิด ตอบ 401

### 4.3 Online / offline

- เมื่อเครื่องเรียก endpoint ข้างบนผ่าน guard อัปเดต `Device.lastSeenAt` (key ผิดไม่นับ)
- **เขียนลงฐานข้อมูลเมื่อค่าเดิมเก่ากว่า 1 นาทีเท่านั้น** กันเขียนทุกคำขอเมื่อมีเครื่องจำนวนมาก
- ถือว่า **online** ถ้าติดต่อมาภายใน 5 นาทีล่าสุด ตอบคำถามเรื่อง online/offline ที่ค้างจากพี่เลี้ยงไปด้วย
- `GET /devices/{deviceId}/status` (#247) เพิ่ม `lastSeenAt` และ `online` ให้หน้าเว็บและแอปใช้ เป็นการเพิ่ม field
  แอปเดิมไม่กระทบ

### 4.4 ข้อกำหนดของเครื่อง (แอปจำลองต้องทำตาม)

- รอตาม `pollAfterSeconds` เป็นอย่างน้อยก่อนดึงครั้งถัดไป
- เรียกไม่สำเร็จ (เน็ตหลุด, 5xx) ให้รอนานขึ้นเรื่อยๆ (เช่น 30, 60, 120 วินาที ไม่เกิน 5 นาที) ไม่ยิงรัว
- ทำงานทีละงานตามลำดับใน `jobs`
- รายงานผลซ้ำได้ถ้าไม่แน่ใจว่าส่งถึง หยุดส่งซ้ำเมื่อได้ 200 ไม่ว่า `accepted` เป็นอะไร
- 401 แปลว่า key ผิดหรือถูกออกใหม่ ให้หยุดและแจ้งผู้ใช้ ไม่ยิงซ้ำ

## 5. Config ปัจจุบันของเครื่องหลังรายงานว่าสำเร็จ (ต้องแก้ก่อนทดสอบ)

ตอนนี้ "Config ปัจจุบันของเครื่อง" (`DeviceService.getBaseConfigForDevice()`) หาจาก **Task ล่าสุดที่ช่างทำเสร็จ**
เท่านั้น ไม่ได้ดูผลของ Rollout เลย ผลคือถ้าเครื่องรายงานว่าสำเร็จ หน้ารายละเอียดอุปกรณ์และหน้าขอแก้ค่าในแอป
ช่างจะยังแสดง Config เดิม ปัญหานี้มีอยู่แล้วในโหมด `mock` ด้วย แต่ไม่เคยเห็นเพราะยังไม่เคยทดสอบครบวงจร

**เสนอ:** Config ปัจจุบัน = รายการที่ใหม่กว่าระหว่าง Task ที่ทำเสร็จล่าสุด กับ Rollout target ของ Config ที่สำเร็จ
ล่าสุด (เทียบเวลาที่บันทึกผล) แก้ที่ฟังก์ชันเดียว ไม่เพิ่มคอลัมน์ ไม่เพิ่ม FK Rollback ที่สำเร็จก็ทำให้ Config ปัจจุบัน
กลับเป็นค่าเก่าเองโดยอัตโนมัติ

**กระทบ B:** ฟังก์ชันนี้อยู่ในโมดูลของ A แต่แอปช่างใช้ผลของมัน (`GET /devices/{deviceId}/config`) หน้าจอแอปไม่ต้องแก้
แค่จะเห็น Config ที่ถูกต้องขึ้น ทั้งโหมด `mock` และ `real`

## 6. Schema (additive ทั้งหมด ไม่มี FK ใหม่)

| คอลัมน์ | ขั้น | ใช้ทำอะไร |
|---|---|---|
| `Device.lastSeenAt DateTime?` | 1 | online / offline |
| `CampaignRollout.applyMode String?` | 1 | โหมดตอนปล่อย (`mock` / `real`) `null` = Rollout เก่าก่อนมีคอลัมน์นี้ ถือเป็น `mock` (หัวข้อ 3) |
| `CampaignRollout.pullTimeoutHours Int?` และ `applyTimeoutMinutes Int?` | 1 | เวลารอของแต่ละ Rollout `null` ใช้ค่าเริ่มต้น (หัวข้อ 16) |
| `CampaignRolloutTarget.pulledAt DateTime?` | 1 | แยก Waiting กับ Applying, ใช้นับเวลารอ, ใช้เลือกเครื่องตอน Rollback (หัวข้อ 3.1) |

## 10. มือถือเข้าถึง backend อย่างไร และข้อจำกัดที่ยอมรับในการทดสอบ

backend รันบนคอมพิวเตอร์ของ A มือถือเรียก `localhost` ไม่ได้ จึงต้องมี URL ที่ชี้มาหาเครื่องนั้น

**เลือก: Cloudflare Tunnel (ฟรี) จากเครื่องที่รัน backend** (B เห็นด้วย 15 ต.ค.) ได้ URL สาธารณะแบบ HTTPS ชั่วคราว
(เช่น `https://xxxx.trycloudflare.com`) เปิดเฉพาะตอนทดสอบ

| เทียบกับ | เหตุผลที่ไม่เลือกตอนนี้ |
|---|---|
| Wi-Fi วงเดียวกัน (`http://192.168.x.x`) | มือถือต้องอยู่ใกล้เครื่อง ใช้ 4G ไม่ได้ Wi-Fi บางที่บล็อกอุปกรณ์ในวงคุยกันเอง และวิ่งแบบไม่เข้ารหัส ใช้เป็นแผนสำรอง |
| Deploy ขึ้นคลาวด์ฟรี (Render + Supabase/Neon) | เอาโค้ดของบริษัทไปไว้ที่ผู้ให้บริการภายนอก ต้องได้รับอนุญาตจากพี่เลี้ยงก่อน |

ข้อดีของ tunnel: ไม่ต้อง deploy อะไร, มือถือใช้ 4G ได้, ได้ HTTPS (API key และค่า sensitive ไม่วิ่งแบบไม่เข้ารหัส),
ปิดแล้ว URL หายไป ไม่มีโค้ดหรือข้อมูลไปเก็บที่อื่น

ข้อจำกัดที่ยอมรับ:
- เครื่องที่รัน backend ต้องเปิดอยู่ตลอดการทดสอบ
- URL ฟรีเปลี่ยนทุกครั้งที่เปิด tunnel ใหม่ ต้องแก้ URL ในแอปทุกรอบ
- อยู่หลัง proxy ของ Cloudflare ต้องตั้ง `TRUST_PROXY=1` ตอนเปิด tunnel ไม่งั้น IP ใน Audit Log จะเป็นของ proxy ทุกแถว
  และ**ต้องเอาออกเมื่อปิด tunnel** (ตามข้อห้ามใน CLAUDE.md) ถ้าวันหน้ามี reverse proxy ของเราเองคั่นอีกชั้น ค่านี้ต้อง
  เท่ากับจำนวน proxy จริง
- ใช้ข้อมูลทดสอบเท่านั้น API ของ backend ทั้งหมด (รวม `/auth/login`) เข้าถึงได้จากภายนอกระหว่างที่ tunnel เปิด จึงต้อง
  ตั้ง `JWT_SECRET` เป็นค่าสุ่มจริง และ**เปลี่ยนรหัสบัญชีทดสอบ** (`*.test` ทุกบทบาทรวม `superadmin.test` ใช้ `password123`
  ซึ่งอยู่ในโค้ดบน GitHub) ด้วย `npm run test-users:set-password` ตามรหัสใน `TEST_USERS_PASSWORD` ของ `.env`
  ตั้ง `TRUST_PROXY` แล้ว backend จะไม่ยอมเริ่มถ้ายังไม่ได้ทำ 2 อย่างนี้ (#323) จึงลืมไม่ได้
- แจ้งพี่เลี้ยงก่อนว่าจะเปิด tunnel ชั่วคราวตอนทดสอบ
- ทุกคำขอต้องตรวจ API key ด้วย bcrypt มือถือ 5 เครื่องทุก 30 วินาทีไม่มีปัญหา แต่ยังไม่มี rate limit ฝั่ง backend

## 11. แผนทดสอบด้วยมือถือ 5 เครื่อง

**เตรียม**
1. ตั้ง `TEST_USERS_PASSWORD` ใน `.env` แล้วรัน `npm run test-users:set-password` ในโฟลเดอร์ backend (login ด้วยชื่อ
   บัญชีเดิมและรหัสใหม่ บอกรหัสให้คนร่วมทดสอบทางช่องทางส่วนตัว)
2. ตั้ง `DEVICE_CONFIG_APPLY_MODE=real` และ `TRUST_PROXY=1` แล้วรีสตาร์ต backend เปิด tunnel ตามหัวข้อ 10
3. ลงทะเบียนอุปกรณ์ 5 เครื่องบนเว็บ (หรือกด "ออก API Key ใหม่" ให้เครื่องที่มีอยู่) กรอก URL, Device ID และ key ในแอป
4. สร้าง Campaign ที่มี**เฉพาะ 5 เครื่องนี้** (อุปกรณ์ตัวอย่างที่ไม่มีมือถือคู่จะค้าง Waiting จนหมดเวลารอ)
5. สร้าง Rollout ด้วย Config ที่อนุมัติแล้ว ให้ 1 เครื่องมีค่าเฉพาะเครื่อง อนุมัติแล้วปล่อย

**กรณีทดสอบ**
1. **ทุกเครื่องสำเร็จ:** เว็บเห็น Waiting → Applying → สำเร็จ นับได้ 5/5, Rollout เป็น `completed`, เครื่องที่มีค่า
   เฉพาะเครื่องได้ค่าที่ถูกต้อง และหน้ารายละเอียดอุปกรณ์แสดง Config ใหม่ (หัวข้อ 5)
2. **1 เครื่องล้มเหลวระหว่างทาง (Auto Pause):** เปิดแอปทีละเครื่อง ให้เครื่องแรกล้มเหลวก่อนเครื่องอื่นดึงงาน (ดูข้อจำกัดใน
   หัวข้อ 15.7) Rollout หยุดเอง เครื่องที่ยังไม่ดึงไม่ได้งาน มี Incident และแจ้งเตือน Operation
3. **Resume:** กด Resume เครื่องที่เหลือได้งานต่อ Incident เป็น `investigating`
4. **Rollback:** ทำกรณี 2 ใหม่ ให้อีกเครื่องดึงงานไปแล้วแต่ยังไม่กดผล แล้วกด Rollback เครื่องที่สำเร็จและเครื่องที่ดึงไป
   แล้วต้องได้ Config เก่า (หัวข้อ 3.1) Incident เป็น `rolled_back`
5. **เครื่องสุดท้ายที่รายงานล้มเหลว:** Rollout จบเป็น `completed` ไม่หยุด แต่มี Incident และแจ้งเตือน (หัวข้อ 15)
6. **ปิดเน็ตมือถือ 1 เครื่อง:** เครื่องนั้นเป็น offline ภายใน 5 นาที
7. **เวลารอ (หัวข้อ 16):** ตั้งเวลารอสั้นตอนสร้าง Rollout (เช่น 1 ชั่วโมง / 2 นาที) ใช้โหมดกดเอง
   - เครื่องที่ 1 ดึงงานแล้วไม่กดผล หรือปิดแอป / เปิดโหมดเครื่องบินทันทีหลังดึง (สมมติกล่องดับหรือสัญญาณหายหลังได้ Config)
     ครบ 2 นาที ได้ `failed` และ Incident `critical`
   - เครื่องที่ 2 ปิดแอปไว้ไม่ดึงเลย ครบเวลาได้ "ข้าม: เครื่องออฟไลน์" แล้วเปิดแอปกลับมา ต้องได้งานต่อและรายงานผลได้
8. **ส่งซ้ำ:** รายงานผลงานเดิม 2 ครั้ง ครั้งที่ 2 ได้ `accepted: false` ตัวเลขไม่นับซ้ำ

**หลังทดสอบ:** ปิด tunnel, เอา `TRUST_PROXY` ออก, ตั้งโหมดกลับเป็น `mock` (Rollout ที่ปล่อยตอน `real` ยังทำงานตาม
โหมดของตัวเองต่อจนจบ ตามหัวข้อ 3) ถ้าอยากคืนรหัสบัญชีทดสอบเป็น `password123` ตั้ง `TEST_USERS_PASSWORD=password123`
แล้วรันสคริปต์อีกครั้ง (ทำได้เฉพาะหลังเอา `TRUST_PROXY` ออกแล้ว)

## 15. Rollout ล้มเหลวแล้วสร้าง Incident อัตโนมัติ

### 15.1 ปัญหาตอนนี้

เกณฑ์ Auto Pause คือ 5% ตาม `GPS_Config_Firmware_Center_Design.pdf` §11.2 คำนวณจากจำนวนเครื่องที่ล้มในรอบนี้ หารด้วย
จำนวนเครื่องทั้งหมดใน Rollout หยุดเมื่อ**เกิน** 5% และยังมีเครื่องที่รอผลอยู่ (นับใหม่หลัง Resume)

- **Auto Pause แล้วเงียบ:** Rollout เปลี่ยนเป็น `paused` ไม่มีใครได้รับแจ้ง ไม่มี Incident
- **เครื่องสุดท้ายล้มเหลวแล้วเงียบ:** Rollout จบเป็น `completed` ผลล้มเหลวอยู่แค่ในหน้า Rollout คำว่า "เสร็จสิ้น"
  ทำให้เข้าใจผิดได้ว่าเรียบร้อย ถ้าเพิ่ม Incident แค่ตอน Auto Pause เครื่องที่ล้มเหมือนกันจะได้ Incident หรือไม่
  ขึ้นอยู่กับว่ารายงานเป็นลำดับที่เท่าไร

### 15.2 เมื่อไรสร้าง Incident

| สถานการณ์ | ผล |
|---|---|
| มีเครื่องดึงงานแล้วเงียบจนหมดเวลา (หัวข้อ 16) อย่างน้อย 1 เครื่อง | Incident `critical` + แจ้งเตือน (ตาม PDF §11.2) |
| ล้มระหว่างทาง เกิน 5% (Auto Pause) | Incident `high` + แจ้งเตือน |
| จบแล้ว อัตราล้มเหลวเกิน 5% | Incident `high` + แจ้งเตือน |
| จบแล้ว มีล้มบ้างแต่ไม่เกิน 5% | Incident `medium` + แจ้งเตือน |
| จบแล้ว ไม่มีเครื่องล้ม แต่มีเครื่องถูกข้ามเพราะออฟไลน์ | Incident `low` + แจ้งเตือน (ให้ Operation ตามเครื่องที่ยังไม่ได้ Config) |
| จบแล้ว ทุกเครื่องสำเร็จ | ไม่สร้าง |

ถ้าเข้าหลายแถว ใช้ severity ที่สูงที่สุด

### 15.3 รายละเอียด Incident

| field | ค่า |
|---|---|
| `title` | "Rollout หยุดอัตโนมัติ: (ชื่อ Campaign)" หรือ "Rollout จบแต่มีเครื่องที่ไม่สำเร็จ: (ชื่อ Campaign)" |
| `status` | `open` |
| `source` | `rollout-failure` (ค่าใหม่ `source` เป็น string อิสระอยู่แล้ว ไม่แก้ schema) |
| `relatedConfigId` / `relatedFirmwareId` | Config หรือ Firmware ของ Rollout |
| `metadata` | `rolloutId`, `campaignId`, จำนวนล้มเหลว / ข้าม / ทั้งหมด, อัตราล้มเหลว, เครื่องที่ล้ม (ไม่เกิน 20 เครื่อง) |

- **1 Rollout มีได้ 1 Incident** หยุดเองหลายรอบหรือหยุดแล้วจบทีหลัง ให้อัปเดต Incident เดิม (ตัวเลข, severity
  เป็นค่าที่สูงกว่า) และเปลี่ยนสถานะกลับเป็น `open` ไม่สร้างใหม่
- Rollback สร้าง Rollout ใหม่ ถ้า Rollback ล้มเหลวด้วย จะได้ Incident ของรอบ Rollback แยกต่างหาก ใน `metadata` อ้าง
  `rolloutId` ของรอบต้นเรื่องผ่าน `rollbackOfId`
- การสร้างโดยระบบไม่ลง Audit Log เหมือน Incident อัตโนมัติจาก `config-sync-writer` ที่มีอยู่ ส่วนการ Resume / Rollback
  ของ Operation ยังลงครบ

### 15.4 สถานะ Incident ตามผลของ Rollout (อัตโนมัติ)

| Operation ทำอะไร / ผล | สถานะ Incident |
|---|---|
| กด Rollback | `rolled_back` |
| กด Resume | `investigating` |
| Rollout จบ และ**ไม่มีเครื่องล้มหรือถูกข้ามในรอบหลัง Resume** | `resolved` พร้อมหมายเหตุ "ปิดอัตโนมัติ: Rollout เสร็จสิ้น" |
| Rollout จบ แต่ยังมีเครื่องล้มหรือถูกข้าม | คง `open` ไว้ให้ Operation ตัดสินใจ |
| ผลล่าช้า (หัวข้อ 16.4) ทำให้ Rollout ที่จบแล้วไม่มีเครื่องค้าง | อัปเดตตัวเลขใน Incident ไม่ปิดเอง ให้ Operation ปิด |

Operation ยังเปลี่ยนสถานะเองได้ตามปกติ เช่นปิดเองพร้อมหมายเหตุถ้าเป็นแค่เครื่องเสีย หรือส่งช่างไปดูเครื่องนั้น

### 15.5 แบ่งงาน (ไม่มีใครแตะโมดูลของอีกคน)

ใช้รูปแบบเดียวกับ `config-sync-writer` ที่มีอยู่: โมดูล campaign ส่ง event แล้วโมดูล incident (A) กับโมดูล
notification (B) ต่างฟังเอง

- **campaign (A):** ส่ง event 2 ชนิด
  - `rollout-failed` ตอน Auto Pause และตอนจบแบบมีเครื่องไม่สำเร็จ (incident และ notification ฟัง)

    ```ts
    {
      rolloutId: string;
      campaignId: string;
      campaignName: string;
      configId: string | null;    // Rollout ของ Firmware ไม่มี configId
      firmwareId: string | null;  // Rollout ของ Config ไม่มี firmwareId
      kind: 'auto-pause' | 'completed-with-failures' | 'completed-with-skipped';
      severity: 'critical' | 'high' | 'medium' | 'low';  // ตามหัวข้อ 15.2
      failureCount: number;
      skippedCount: number;       // เครื่องที่ถูกข้ามเพราะออฟไลน์ (หัวข้อ 16)
      targetCount: number;
      failedDeviceIds: string[];  // ไม่เกิน 20 เครื่อง
      sampleErrors: string[];     // ไม่เกิน 3 รายการ จาก CampaignRolloutTarget.resultDetail
    }
    ```

    ไม่ใส่ `deviceModel` / `protocol` เพราะหาได้จาก `configId` อยู่แล้ว (ตามที่ B ขอ) `severity` คำนวณที่ campaign
    ครั้งเดียว ทั้ง incident และ notification ใช้ค่าเดียวกัน
  - `rollout-status-changed` `{ rolloutId, status }` ตอน Resume / Rollback / จบ ให้ incident ปรับสถานะตามหัวข้อ 15.4
    (เฉพาะ incident ฟัง notification ไม่ต้องทำอะไร)
- **incident (A):** สร้างหรืออัปเดต Incident ตามหัวข้อ 15.2 ถึง 15.4
- **notification (B):** เพิ่มชนิดแจ้งเตือนใหม่ **`rollout_failed`** (เพิ่มค่าใน enum `NotificationType` ต้องมี migration
  แบบ additive) แล้วฟัง `rollout-failed` ส่งให้ Operation ทุกคนที่ active (เหมือน `config-sync-failure-alert.listener.ts`)
  ข้อความประกอบจาก `campaignName`, `failureCount` / `skippedCount` / `targetCount` และ `kind`
  - **ไม่ใช้ `incident_alert` ซ้ำ** เพราะเว็บ (#317) ตั้งหัวข้อของ `incident_alert` ไว้ตายตัวว่า "เขียน Config
    ไม่สำเร็จ" และลิงก์ไปหน้า Config ซึ่งไม่ตรงกับเหตุการณ์นี้ (B ชี้ 15 ต.ค.)
  - payload ของแจ้งเตือนมี `rolloutId`, `campaignId` และ `severity` ไม่มี `incidentId` เพราะ incident กับ notification
    ฟัง event เดียวกันพร้อมกัน listener ฝั่ง notification จึงไม่รู้ id ของ Incident
  - ส่งซ้ำได้ทุกครั้งที่มี event (Auto Pause รอบใหม่หลัง Resume ก็แจ้งใหม่) ไม่ต้องกันซ้ำ
- **เว็บ (A):**
  - เพิ่ม case `rollout_failed` ใน `describeNotification` ลิงก์ไปหน้า Rollout (`/campaigns/{campaignId}/rollouts/{rolloutId}`)
    จัดเป็นแจ้งเตือนด่วนเมื่อ `severity` เป็น `critical` หรือ `high`
  - หน้ารายละเอียด Incident มีลิงก์ไปหน้า Rollout ที่เกี่ยวข้อง

ใช้ได้ทั้งโหมด `mock` และ `real` เพราะทั้งสองโหมดผ่าน `recordTargetResult()` ตัวเดียวกัน

### 15.6 ตั้งใจยังไม่ทำ

- ส่ง Config ซ้ำเฉพาะเครื่องที่ล้ม (ตอนนี้ต้องสร้าง Rollout ใหม่)

### 15.7 ข้อจำกัดของ Auto Pause ในโหมด `real`

Auto Pause หยุดได้เฉพาะเครื่องที่**ยังไม่ได้ดึงงาน** ในโหมด `real` ทุกเครื่องดึงงานภายใน 30 วินาทีหลังปล่อย ส่วนผลล้มเหลว
มาทีหลัง ถ้าทุกเครื่องออนไลน์พร้อมกัน ทุกเครื่องจะได้ Config ไปก่อนที่ระบบจะรู้ว่ามีปัญหา Auto Pause จึงแทบไม่ได้ปกป้อง
อะไร (ต่างจากโหมด `mock` ที่ apply ทีละเครื่อง)

- **ขั้นที่ 1:** ยอมรับไว้ การทดสอบกรณี 2 ในหัวข้อ 11 เปิดแอปทีละเครื่อง Rollback (หัวข้อ 3.1) ยังเก็บเครื่องที่ได้
  Config ไปแล้วได้ครบ
- **ทางแก้ระยะยาว:** จำกัดจำนวนเครื่องที่ดึงงานพร้อมกัน เช่น ส่งงานให้ไม่เกิน N เครื่องที่ยังไม่รายงานผล ตรงกับ
  Batch Size / Concurrency ใน PDF §9.1 เพิ่มได้ภายหลังที่ endpoint `jobs` จุดเดียว ไม่กระทบ contract ของเครื่อง

## 16. เวลารอเครื่องที่ไม่ตอบกลับ (Timeout)

### 16.1 ปัญหา

ในโหมด `real` ถ้ากล่องไม่ติดต่อมาเลย (รถจอดนาน กล่องเสีย ไม่มีสัญญาณ) เครื่องนั้นค้าง `pending` ตลอดไป
Rollout ไม่มีวันจบ Auto Pause ไม่ทำงาน และเปิด Rollout ใหม่ให้กลุ่มเดิมไม่ได้ (กลุ่มหนึ่งมี Rollout ค้างได้ทีละรอบ)

### 16.2 ที่มาใน PDF

`GPS_Config_Firmware_Center_Design.pdf` ระบุไว้ระดับหัวข้อ ไม่มีตัวเลข:
- §9.1 Campaign มี Execution: "Batch Size, Concurrency, **Timeout**, Retry Policy"
- §10.1 Pre-check ก่อนอัปเดต: "**Device Online**" (เครื่องออฟไลน์ยังไม่พร้อมรับงาน ไม่ใช่ความล้มเหลว)
- §11.2 กฎอัตโนมัติ: "**Offline หลังอัปเดตเกินเกณฑ์ → Critical Alert** และหยุด Batch ถัดไป"

### 16.3 กติกา

| กรณี | เวลารอ (ค่าเริ่มต้น) | เริ่มนับเมื่อ | ผลเมื่อครบเวลา | นับเข้า Auto Pause |
|---|---|---|---|---|
| **ไม่มาดึงงานเลย** (Waiting) | 72 ชั่วโมง | `activeWindowStartedAt` (ปล่อย หรือ Resume ครั้งล่าสุด) | `skipped_offline` "ข้าม: เครื่องออฟไลน์" | ไม่นับ (ตาม §10.1 เครื่องออฟไลน์ยังไม่พร้อม ไม่ใช่ Config ผิด) |
| **ดึงไปแล้วเงียบ** (Applying) | 30 นาที | `pulledAt` | `failed` "ดึงงานแล้วไม่รายงานผลภายใน 30 นาที" | นับ |

- 72 ชั่วโมงครอบคลุมรถที่จอดช่วงสุดสัปดาห์ 30 นาทีเผื่อเวลากล่องใช้ค่า ทั้งสองค่าเป็น**ค่าเริ่มต้น** Operation ปรับได้ตอน
  สร้าง Rollout (ตาม §9.1) และจะยืนยันตัวเลขกับพี่เลี้ยงอีกครั้ง ถ้าพี่เลี้ยงให้ค่าอื่นก็แก้แค่ค่าเริ่มต้น
- **ช่วงที่ Rollout `paused`:** เวลารอแบบไม่มาดึงหยุดนับ (เครื่องไม่ได้งานอยู่แล้ว) และนับใหม่จาก Resume ส่วนเวลารอแบบดึงแล้ว
  เงียบยังนับต่อ เพราะเครื่องได้ Config ไปแล้วจริง
- `failed` จากการดึงแล้วเงียบผ่าน `recordTargetResult()` ตามปกติ จึงได้ Auto Pause และ Incident `critical` ตามหัวข้อ 15.2
- เครื่อง `skipped_offline` นับว่า "มีผลแล้ว" Rollout จึงจบได้ และได้ Incident ตามหัวข้อ 15.2
- Rollback สร้าง Rollout ใหม่ ใช้เวลารอและ `applyMode` เดียวกับรอบต้นเรื่อง

### 16.4 เครื่องที่กลับมาหลังหมดเวลา

- เครื่อง `skipped_offline` ที่กลับมาออนไลน์ **ยังได้งานนั้น** ถ้า Rollout เป็น `active` หรือ `completed` (ไม่ใช่ `cancelled`)
  และเครื่องยังไม่มีงานใหม่กว่าของ payload ชนิดเดียวกัน (ถ้ามี Rollout ใหม่กว่า เครื่องจะได้งานของรอบนั้นแทน)
- รายงานผลได้ตามปกติ `skipped_offline` เปลี่ยนเป็น `success` หรือ `failed` พร้อมหมายเหตุ "ล่าช้า" นับตัวเลขใหม่และอัปเดต
  Incident ตามหัวข้อ 15.4 Rollout ที่ `completed` แล้วไม่เปิดใหม่ และผลล่าช้าไม่ทำให้เกิด Auto Pause
- เครื่อง `failed` จากการดึงแล้วเงียบ ถ้ารายงานผลทีหลัง **ไม่เปลี่ยนผล** (ตัดสินไปแล้วและอาจทำให้เกิด Auto Pause ไปแล้ว)
  ตอบ `already-reported` และเก็บข้อความไว้ให้ Operation เห็น

### 16.5 วิธีทำ

- งานตามเวลาทุก 5 นาทีด้วย `@nestjs/schedule` (มีใช้อยู่แล้วกับงานลบ Config อัตโนมัติ)
- ตรวจเฉพาะ Rollout ที่ `applyMode = real`: เวลารอแบบไม่มาดึงตรวจเมื่อ `active`, แบบดึงแล้วเงียบตรวจเมื่อ `active` หรือ `paused`
- เปลี่ยนสถานะแบบมีเงื่อนไข (`updateMany` ที่ระบุสถานะเดิม) กันชนกับเครื่องที่รายงานผลเข้ามาพร้อมกัน แบบเดียวกับที่
  `recordTargetResult()` ทำอยู่
- ทุกคอลัมน์ใหม่เป็น additive ตามหัวข้อ 6

ตรวจกับโค้ดจริงอีกรอบแล้วพบช่องโหว่ จึงปรับดังนี้ (ไม่กระทบคำตอบที่ B ให้ไว้)

| Rollback ส่ง Config เก่าเฉพาะเครื่องที่สำเร็จ เครื่องที่ดึงไปแล้วแต่ยังไม่รายงานจะค้างกับ Config ที่มีปัญหา | หัวข้อ 3.1 |
