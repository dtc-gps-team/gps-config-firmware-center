# ข้อเสนอออกแบบ: อุปกรณ์ดึง Config เองและรายงานผล (ทดสอบด้วยมือถือจำลองกล่อง GPS)

> เอกสารนี้เป็น**ข้อเสนอ ยังไม่ใช่มติ** เขียนให้ kittiphong (B) รีวิวก่อนลงมือทำ ตาม pattern เดียวกับ
> `docs/14` และ `docs/17` ยังไม่แก้ schema และยังไม่เขียนโค้ดใดๆ จนกว่า B เห็นด้วย
>
> **ที่มา:** รีวิวกับพี่เลี้ยง 12 ต.ค. 2569 ให้ทดสอบด้วยมือถือ 5 เครื่อง แต่ละเครื่องจำลองเป็นกล่อง GPS
> แล้วพิสูจน์ว่า Config ที่ปล่อยจากระบบไปถึงเครื่องจริง เครื่องรายงานผลสำเร็จหรือล้มเหลวกลับมาได้
> และหน้าเว็บนับจำนวนถูกต้อง พี่เลี้ยงยืนยันในวันเดียวกันว่าให้ใช้ API key ต่อเครื่องแบบที่มีอยู่ไปก่อน
>
> **ความสัมพันธ์กับเอกสารอื่น:** เอกสารนี้คือการทำ PR 2 และ PR 3 ที่ `docs/14` วางแผนไว้ โดยปรับให้ตรง
> กับระบบปัจจุบัน (Campaign Rollout, ค่าเฉพาะเครื่อง) ส่วน `docs/17` เคยเขียนไว้ว่าเรื่องนี้จะเป็นข้อเสนอ
> ของ B ถ้า B มีร่างอยู่แล้ว รบกวนแจ้งในรีวิว จะได้รวมกันเป็นฉบับเดียว
>
> เรื่อง Rollout ล้มเหลวแล้วสร้าง Incident อัตโนมัติ (รวม Auto Pause) อยู่ในหัวข้อ 15 เพราะเป็นสิ่งที่พี่เลี้ยงจะเห็น
> ในการทดสอบเดียวกัน และต้องมีงานฝั่ง B ด้วย จึงรวมไว้ให้รีวิวครั้งเดียว

## 1. เป้าหมายและขอบเขต

| | ขั้นที่ 1 (เอกสารนี้) | ขั้นที่ 2 (ออกแบบเผื่อไว้ ทำทีหลัง) |
|---|---|---|
| สิ่งที่ส่งเข้าเครื่อง | Config | Firmware |
| เครื่องทำอะไร | ดึงงาน, ใช้ค่า, รายงานผล | ดาวน์โหลดไฟล์, ตรวจ checksum, รายงานผล |
| endpoint | 2 ตัว (หัวข้อ 4) | ใช้ 2 ตัวเดิม เพิ่มชนิดงาน |

**ทำไม Firmware ไว้ขั้นที่ 2:** พี่เลี้ยงขอเรื่อง Config โดยตรง และมือถือติดตั้ง Firmware จริงไม่ได้ จึงพิสูจน์ได้
น้อยกว่า Config มาก แต่ contract ทุกตัวมีชนิดงาน (`payloadType`) ตั้งแต่แรก ขั้นที่ 2 จึงเพิ่มได้โดยไม่ต้อง
รื้อของเดิม ทั้งฝั่ง backend และแอปจำลอง

## 2. ของที่มีอยู่แล้วและจะใช้ต่อ

| ของเดิม | ใช้ทำอะไรในงานนี้ |
|---|---|
| `Device.apiKeyHash` และ `DeviceApiKeyGuard` (#157 PR 1) | ยืนยันตัวตนของเครื่อง ตอนนี้ guard มีแล้วแต่ยังไม่มี endpoint ไหนใช้ |
| ปุ่ม "ออก API Key ใหม่" บนเว็บ | เอา key ไปใส่ในแอปจำลอง |
| `CampaignRolloutTarget` สถานะ `pending` | ใช้เป็น "งานที่รอเครื่องนี้ทำ" ไม่ต้องสร้างตารางงานใหม่ |
| `CampaignRolloutService.recordTargetResult()` | นับ success/failure, Auto Pause, ปิด Rollout เมื่อครบ ใช้ต่อได้ทั้งหมด |
| `mergeApprovedOverride()` | รวมค่าเฉพาะเครื่องที่อนุมัติแล้วเข้ากับ Config ก่อนส่งให้เครื่อง (ตามที่ B ขอไว้ใน #290 ข้อ 6) |
| env `DEVICE_CONFIG_APPLY_MODE` (`mock` / `real`) | ตอนนี้ `real` แค่ throw ว่ายังไม่รองรับ งานนี้ทำให้ `real` ใช้งานได้จริง |

## 3. หลักการ

- **`mock` (ค่าเริ่มต้น ไม่เปลี่ยน):** ทำงานเหมือนเดิมทุกอย่าง ปล่อย Rollout แล้ว backend apply ให้ทุกเครื่องทันที
  เดโมและเทสต์เดิมไม่กระทบ
- **`real`:** ปล่อย Rollout แล้ว backend **ไม่** apply เอง เครื่องเป้าหมายค้างเป็น `pending` จนกว่าเครื่องจะ
  มาดึงงานและรายงานผลเอง
- Auto Pause, Resume, Rollback และการนับผล ใช้กลไกเดิมทั้งหมด
- Rollback ของ Config ในโหมด `real` ทำงานได้เองโดยไม่ต้องแก้: Rollback สร้างเป้าหมายใหม่เป็น `pending`
  เครื่องก็มาดึง Config เก่าไปเหมือนงานปกติ
- Rollback ของ Firmware (สลับพาร์ทิชัน) ยังเป็น mock แยกต่างหาก ไม่อยู่ในขอบเขตนี้

## 4. Endpoint ที่อุปกรณ์เรียก

ยืนยันตัวตนด้วย header `X-Device-Api-Key` ผ่าน `DeviceApiKeyGuard` (ไม่ใช่ JWT เพราะอุปกรณ์ไม่ใช่ผู้ใช้)

**เรื่อง path:** `docs/14` เคยร่างไว้เป็น `GET /devices/{deviceId}/config` แต่ path นี้ถูกใช้แล้วโดย endpoint ของ
staff (`getCurrentConfig` ที่ใช้ JWT) จึงเสนอ prefix ใหม่ `/device-sync/` แยกให้ชัดว่าเป็นของอุปกรณ์

### 4.1 `GET /device-sync/{deviceId}/jobs` ดึงงานที่รออยู่

```json
{
  "serverTime": "2026-10-20T10:00:00Z",
  "pollAfterSeconds": 30,
  "jobs": [
    {
      "jobId": "id ของ CampaignRolloutTarget",
      "rolloutId": "...",
      "createdAt": "2026-10-20T09:58:00Z",
      "payloadType": "Config",
      "config": {
        "configId": "...",
        "name": "GT06N มาตรฐาน",
        "deviceModel": "GT06N",
        "protocol": "TCP",
        "fields": { "SPEED_LIMIT": 180, "APN": "internet" }
      }
    }
  ]
}
```

- คืนเฉพาะงานของ Rollout ที่สถานะ `active` ถ้า Rollout ถูก `paused` จะไม่แจกงานนั้นอีก นี่คือสิ่งที่ทำให้
  Auto Pause หยุดเครื่องที่เหลือได้จริงในโหมด `real`
- `fields` คือค่าหลัง `mergeApprovedOverride()` ค่าที่ sensitive ส่งค่าจริง เพราะเครื่องต้องใช้งาน
- **เรียงตาม `createdAt` จากเก่าไปใหม่ เครื่องต้องทำทีละงานตามลำดับ** งานสุดท้ายคือค่าที่ใช้จริง
  (กรณีเครื่องอยู่ใน 2 Rollout ที่ active พร้อมกัน)
- ไม่มีงาน คืน `"jobs": []` (200) ไม่ใช่ 404
- ครั้งแรกที่งานถูกแจก บันทึก `pulledAt` ที่ target ให้หน้าเว็บแยกได้ว่า Waiting (ยังไม่มาดึง) หรือ Applying
  (ดึงไปแล้ว รอผล)
- งานที่ถูก "ข้าม: เครื่องออฟไลน์" (หัวข้อ 16) ยังแจกให้เมื่อเครื่องกลับมา ตามเงื่อนไขในหัวข้อ 16.4

### 4.2 `POST /device-sync/{deviceId}/jobs/{jobId}/result` รายงานผล

```json
{ "result": "success", "detail": "ข้อความจากเครื่อง (ไม่บังคับ)" }
```

- `result` เป็น `success` หรือ `failed`
- เรียก `recordTargetResult()` โดยส่ง `rolloutId` ของ job นั้นตรงๆ ไม่เปิด fallback แบบ path ของ Mobile
- **ส่งซ้ำได้ (idempotent):** ถ้า job นั้นมีผลไปแล้ว ตอบ 200 พร้อม `{ "accepted": false }` เพราะมือถือเน็ตหลุดแล้ว
  ส่งซ้ำเป็นเรื่องปกติ ครั้งที่บันทึกผลจริงตอบ `{ "accepted": true }`
- `jobId` ที่ไม่ใช่ของเครื่องนี้ ตอบ 404 (pattern เดียวกับ IDOR Prevention ใน CLAUDE.md)
- ยกเว้นงานที่ถูก "ข้าม: เครื่องออฟไลน์" ยังรับผลได้ ตามหัวข้อ 16.4

### 4.3 Online / offline

- ทุกครั้งที่เครื่องเรียก endpoint ข้างบนผ่าน guard อัปเดต `Device.lastSeenAt`
- ถือว่า **online** ถ้าติดต่อมาภายใน 5 นาทีล่าสุด ตอบคำถามเรื่อง online/offline ที่ค้างจากพี่เลี้ยงไปด้วย

### 4.4 ข้อกำหนดของเครื่อง (แอปจำลองต้องทำตาม)

- รอตาม `pollAfterSeconds` เป็นอย่างน้อยก่อนดึงครั้งถัดไป
- ทำงานทีละงานตามลำดับใน `jobs`
- รายงานผลซ้ำได้ถ้าไม่แน่ใจว่าส่งถึง

## 5. Config ปัจจุบันของเครื่องหลังรายงานว่าสำเร็จ (ต้องแก้ก่อนทดสอบ)

ตอนนี้ "Config ปัจจุบันของเครื่อง" (`DeviceService.getBaseConfigForDevice()`) หาจาก **Task ล่าสุดที่ช่างทำเสร็จ**
เท่านั้น ไม่ได้ดูผลของ Rollout เลย ผลคือถ้าเครื่องรายงานว่าสำเร็จ หน้ารายละเอียดอุปกรณ์และหน้าขอแก้ค่าในแอป
ช่างจะยังแสดง Config เดิม ปัญหานี้มีอยู่แล้วในโหมด `mock` ด้วย แต่ไม่เคยเห็นเพราะยังไม่เคยทดสอบครบวงจร

**เสนอ:** Config ปัจจุบัน = รายการที่ใหม่กว่าระหว่าง Task ที่ทำเสร็จล่าสุด กับ Rollout target ที่สำเร็จล่าสุด (Config)
แก้ที่ฟังก์ชันเดียว ไม่เพิ่มคอลัมน์ ไม่เพิ่ม FK

**กระทบ B:** ฟังก์ชันนี้อยู่ในโมดูลของ A แต่แอปช่างใช้ผลของมัน (`GET /devices/{deviceId}/config`) หน้าจอแอปไม่ต้องแก้
แค่จะเห็น Config ที่ถูกต้องขึ้น

## 7. หน้าเว็บ (A)

- **หน้ารายละเอียด Rollout:** สถานะรายเครื่อง 5 แบบ คือ Waiting (รอเครื่องดึง) / Applying (ดึงแล้วรอผล) / สำเร็จ /
  ล้มเหลว / ข้าม: เครื่องออฟไลน์ พร้อมข้อความจากเครื่อง เวลาที่เหลือก่อนหมดเวลารอ และ "ไม่ติดต่อมาเกิน 5 นาที"
  ที่เครื่องที่เงียบไป ชื่อ Waiting ตรงกับสถานะใน `GPS_Config_Firmware_Center_Design.pdf` §10.3
- **ฟอร์มสร้าง Rollout:** ช่องเวลารอ 2 ช่อง (หัวข้อ 16) มีค่าเริ่มต้นกรอกไว้ให้
- **หน้ารายละเอียดอุปกรณ์:** สถานะ online / offline และเวลาที่ติดต่อล่าสุด

## 8. แอปจำลองกล่อง (B)

อยู่ในส่วนของ B ทั้งหมด A ไม่แตะ

- กรอก URL ของ backend, Device ID และ API key
- ดึงงานตาม `pollAfterSeconds` แสดง Config ที่ได้
- ปุ่ม "สำเร็จ" / "ล้มเหลว" ให้กดเอง และโหมดอัตโนมัติที่ตั้งอัตราล้มเหลวได้ (ใช้ทดสอบ Auto Pause)
- **เป็นโหมดหนึ่งในแอปเดิม ไม่แยกแอป** (B ตอบ 15 ต.ค.) แจกจ่ายให้ทดสอบง่ายกว่า กั้นด้วย flag ไม่ให้ UI โหมดจำลอง
  ปนกับโหมดใช้งานจริง

## 9. ขั้นที่ 2: Firmware (ออกแบบเผื่อไว้)

- งานใน `jobs` เพิ่มชนิด `"Firmware"`:
  `{ firmwareId, version, fileName, contentType, sizeBytes, checksumSha256, downloadUrl, expiresAt }`
- `downloadUrl` เป็นลิงก์ชั่วคราวจาก MinIO (presigned) backend ไม่ส่งไฟล์ผ่าน endpoint เอง
- **ไม่จำกัดนามสกุลไฟล์** ตามที่พี่เลี้ยงบอกว่าไฟล์ Firmware ตอนนี้มีหลายแบบ ระบบตอนนี้ก็ไม่ได้จำกัดอยู่แล้ว
  เครื่องตรวจความถูกต้องด้วยขนาดไฟล์และ checksum แทน ไม่ดูจากนามสกุล
- คำนวณ checksum ตอนอัปโหลด ไฟล์ที่อัปโหลดก่อนหน้านี้ไม่มี checksum (`null`) ให้เครื่องข้ามการตรวจ
- env `DEVICE_FIRMWARE_APPLY_MODE` (`mock` ค่าเริ่มต้น / `real`) แบบเดียวกับ Config
- รายงานผลใช้ endpoint 4.2 ตัวเดิม

## 10. มือถือเข้าถึง backend อย่างไร และข้อจำกัดที่ยอมรับในการทดสอบ

backend รันบนคอมพิวเตอร์ของ A มือถือเรียก `localhost` ไม่ได้ จึงต้องมี URL ที่ชี้มาหาเครื่องนั้น

**เสนอ: Cloudflare Tunnel (ฟรี) จากเครื่องที่รัน backend** ได้ URL สาธารณะแบบ HTTPS ชั่วคราว
(เช่น `https://xxxx.trycloudflare.com`) เปิดเฉพาะตอนทดสอบ

| เทียบกับ | เหตุผลที่ไม่เลือกตอนนี้ |
|---|---|
| Wi-Fi วงเดียวกัน (`http://192.168.x.x`) | มือถือต้องอยู่ใกล้เครื่อง ใช้ 4G ไม่ได้ Wi-Fi บางที่บล็อกอุปกรณ์ในวงคุยกันเอง และวิ่งแบบไม่เข้ารหัส ใช้เป็นแผนสำรองได้ |
| Deploy ขึ้นคลาวด์ฟรี (Render + Supabase/Neon) | ต้องเขียน Dockerfile ย้ายฐานข้อมูล และเอาโค้ดของบริษัทไปไว้ที่ผู้ให้บริการภายนอก ต้องได้รับอนุญาตจากพี่เลี้ยงก่อน เหมาะกับตอนทำงาน deploy ของ Sprint 4 มากกว่า |

ข้อดีของ tunnel: ไม่ต้อง deploy อะไร, มือถือใช้ 4G ได้, ได้ HTTPS (API key และค่า sensitive ไม่วิ่งแบบไม่เข้ารหัส),
ปิดแล้ว URL หายไป ไม่มีโค้ดหรือข้อมูลไปเก็บที่อื่น

ข้อจำกัดที่ยอมรับ:
- เครื่องที่รัน backend ต้องเปิดอยู่ตลอดการทดสอบ
- URL ฟรีเปลี่ยนทุกครั้งที่เปิด tunnel ใหม่ แอปจำลองจึงต้องให้แก้ URL ได้ (หัวข้อ 8 มีช่องกรอกอยู่แล้ว)
- อยู่หลัง proxy ของ Cloudflare ต้องตั้ง `TRUST_PROXY=1` ตอนเปิด tunnel ไม่งั้น IP ใน Audit Log จะเป็นของ proxy ทุกแถว
  และ**ต้องเอาออกเมื่อปิด tunnel** (ตามข้อห้ามใน CLAUDE.md)
- ใช้ข้อมูลทดสอบเท่านั้น API ของ backend ทั้งหมด (รวม `/auth/login`) เข้าถึงได้จากภายนอกระหว่างที่ tunnel เปิด
- แจ้งพี่เลี้ยงก่อนว่าจะเปิด tunnel ชั่วคราวตอนทดสอบ
- ทุกคำขอต้องตรวจ API key ด้วย bcrypt มือถือ 5 เครื่องทุก 30 วินาทีไม่มีปัญหา แต่ยังไม่มี rate limit ฝั่ง backend

## 11. แผนทดสอบด้วยมือถือ 5 เครื่อง

1. เปิด tunnel ตามหัวข้อ 10 แล้วลงทะเบียนอุปกรณ์ 5 เครื่องบนเว็บ ออก API key กรอกพร้อม URL ของ tunnel ในแอปของแต่ละเครื่อง
2. สร้าง Campaign ที่มี**เฉพาะ 5 เครื่องนี้** (อุปกรณ์ตัวอย่างที่ไม่มีมือถือคู่จะค้าง `pending` ตลอดในโหมด `real`)
3. สร้าง Rollout ด้วย Config ที่อนุมัติแล้ว ให้ 1 เครื่องมีค่าเฉพาะเครื่อง อนุมัติแล้วปล่อย (backend ตั้ง `real`)
4. **ทุกเครื่องสำเร็จ:** เว็บนับได้ 5/5, Rollout เป็น `completed`, เครื่องที่มีค่าเฉพาะเครื่องได้ค่าที่ถูกต้อง และหน้า
   รายละเอียดอุปกรณ์แสดง Config ใหม่ (หัวข้อ 5)
5. **1 เครื่องล้มเหลวระหว่างทาง:** Auto Pause ทำงาน (กับ 5 เครื่อง ล้ม 1 เครื่องคือ 20% เกิน 5%) เครื่องที่ยังไม่ได้ดึง
   ไม่ได้งานอีก มี Incident และแจ้งเตือน Operation จากนั้นทดสอบ Resume และ Rollback (หัวข้อ 15)
6. **เครื่องสุดท้ายที่รายงานล้มเหลว:** Rollout จบเป็น `completed` ไม่หยุด (ไม่มีเครื่องเหลือให้ปกป้อง) แต่ยังมี
   Incident และแจ้งเตือน Operation (หัวข้อ 15)
7. **ปิดเน็ตมือถือ 1 เครื่อง:** เครื่องนั้นเป็น offline ภายใน 5 นาที
8. **เวลารอ (หัวข้อ 16):** ตั้งเวลารอสั้นตอนสร้าง Rollout ทดสอบ (เช่น 1 ชั่วโมง / 2 นาที) ให้ 1 เครื่องเงียบหลังดึงงาน
   ได้ `failed` และ Incident `critical` อีก 1 เครื่องปิดแอปไว้ไม่ดึงเลย ได้ "ข้าม: เครื่องออฟไลน์" แล้วเปิดแอปกลับมา ต้องได้งานต่อ

## 15. Rollout ล้มเหลวแล้วสร้าง Incident อัตโนมัติ

### 15.1 ปัญหาตอนนี้

เกณฑ์ Auto Pause คือ 5% ตาม `GPS_Config_Firmware_Center_Design.pdf` §11.2 คำนวณจากจำนวนเครื่องที่ล้มในรอบนี้ หารด้วย
จำนวนเครื่องทั้งหมดใน Rollout หยุดเมื่อ**เกิน** 5% และยังมีเครื่องที่รอผลอยู่ (นับใหม่หลัง Resume)

- **Auto Pause แล้วเงียบ:** Rollout เปลี่ยนเป็น `paused` ไม่มีใครได้รับแจ้ง ไม่มี Incident
- **เครื่องสุดท้ายล้มเหลวแล้วเงียบ:** Rollout จบเป็น `completed` ผลล้มเหลวอยู่แค่ในหน้า Rollout คำว่า "เสร็จสิ้น"
  ทำให้เข้าใจผิดได้ว่าเรียบร้อย ถ้าเพิ่ม Incident แค่ตอน Auto Pause เครื่องที่ล้มเหมือนกันจะได้ Incident หรือไม่
  ขึ้นอยู่กับว่ารายงานเป็นลำดับที่เท่าไร

### 15.2 เมื่อไรสร้าง Incident

| สถานการณ์ | ผล |
|---|---|
| ล้มระหว่างทาง เกิน 5% (Auto Pause) | Incident `high` + แจ้งเตือน |
| จบแล้ว อัตราล้มเหลวเกิน 5% | Incident `high` + แจ้งเตือน |
| จบแล้ว มีล้มบ้างแต่ไม่เกิน 5% | Incident `medium` + แจ้งเตือน |
| จบแล้ว ไม่มีเครื่องล้มเลย | ไม่สร้าง |

### 15.3 รายละเอียด Incident

| field | ค่า |
|---|---|
| `title` | "Rollout หยุดอัตโนมัติ: (ชื่อ Campaign)" หรือ "Rollout จบแต่มีเครื่องล้มเหลว: (ชื่อ Campaign)" |
| `status` | `open` |
| `source` | `rollout-failure` (ค่าใหม่ `source` เป็น string อิสระอยู่แล้ว ไม่แก้ schema) |
| `relatedConfigId` / `relatedFirmwareId` | Config หรือ Firmware ของ Rollout |
| `metadata` | `rolloutId`, `campaignId`, จำนวนล้มเหลว / ทั้งหมด, อัตราล้มเหลว, เครื่องที่ล้ม (ไม่เกิน 20 เครื่อง) |

- **1 Rollout มีได้ 1 Incident** หยุดเองหลายรอบหรือหยุดแล้วจบทีหลัง ให้อัปเดต Incident เดิม (ตัวเลข, severity
  เป็นค่าที่สูงกว่า) และเปลี่ยนสถานะกลับเป็น `open` ไม่สร้างใหม่
- การสร้างโดยระบบไม่ลง Audit Log เหมือน Incident อัตโนมัติจาก `config-sync-writer` ที่มีอยู่ ส่วนการ Resume / Rollback
  ของ Operation ยังลงครบ

### 15.4 สถานะ Incident ตามผลของ Rollout (อัตโนมัติ)

| Operation ทำอะไร / ผล | สถานะ Incident |
|---|---|
| กด Rollback | `rolled_back` |
| กด Resume | `investigating` |
| Rollout จบ และ**ไม่มีเครื่องล้มในรอบหลัง Resume** | `resolved` พร้อมหมายเหตุ "ปิดอัตโนมัติ: Rollout เสร็จสิ้น" |
| Rollout จบ แต่ยังมีเครื่องล้ม | คง `open` ไว้ให้ Operation ตัดสินใจ |

Operation ยังเปลี่ยนสถานะเองได้ตามปกติ เช่นปิดเองพร้อมหมายเหตุถ้าเป็นแค่เครื่องเสีย หรือส่งช่างไปดูเครื่องนั้น

### 15.5 แบ่งงาน (ไม่มีใครแตะโมดูลของอีกคน)

ใช้รูปแบบเดียวกับ `config-sync-writer` ที่มีอยู่: โมดูล campaign ส่ง event แล้วโมดูล incident (A) กับโมดูล
notification (B) ต่างฟังเอง

- **campaign (A):** ส่ง event `rollout-failed` ตอน Auto Pause และตอนจบแบบมีเครื่องล้ม และส่ง event ตอน
  Resume / Rollback / จบ ให้ incident ปรับสถานะ

  ```ts
  {
    rolloutId: string;
    campaignId: string;
    campaignName: string;
    configId: string | null;    // Rollout ของ Firmware ไม่มี configId
    firmwareId: string | null;  // Rollout ของ Config ไม่มี firmwareId
    kind: 'auto-pause' | 'completed-with-failures';
    failureCount: number;
    targetCount: number;
    failedDeviceIds: string[];  // ไม่เกิน 20 เครื่อง
    sampleErrors: string[];     // ไม่เกิน 3 รายการ จาก CampaignRolloutTarget.resultDetail
  }
  ```

  ไม่ใส่ `deviceModel` / `protocol` เพราะหาได้จาก `configId` อยู่แล้ว (ตามที่ B ขอ)
- **incident (A):** สร้างหรืออัปเดต Incident ตามหัวข้อ 15.2 ถึง 15.4
- **notification (B):** เพิ่มชนิดแจ้งเตือนใหม่ **`rollout_failed`** (เพิ่มค่าใน enum `NotificationType` ต้องมี migration
  แบบ additive) แล้วฟัง `rollout-failed` ส่งให้ Operation ทุกคนที่ active (เหมือน `config-sync-failure-alert.listener.ts`)
  ข้อความประกอบจาก `campaignName`, `failureCount` / `targetCount` และ `kind`
  - **ไม่ใช้ `incident_alert` ซ้ำ** เพราะเว็บ (#317) ตั้งหัวข้อของ `incident_alert` ไว้ตายตัวว่า "เขียน Config
    ไม่สำเร็จ" และลิงก์ไปหน้า Config ซึ่งไม่ตรงกับเหตุการณ์นี้ (B ชี้ 15 ต.ค.)
  - payload ของแจ้งเตือนมี `rolloutId` และ `campaignId` ไม่มี `incidentId` เพราะ incident กับ notification ฟัง event
    เดียวกันพร้อมกัน listener ฝั่ง notification จึงไม่รู้ id ของ Incident
- **เว็บ (A):**
  - เพิ่ม case `rollout_failed` ใน `describeNotification` ลิงก์ไปหน้า Rollout ด้วย `campaignId` / `rolloutId`
    จัดเป็นแจ้งเตือนด่วนแบบเดียวกับ `incident_alert`
  - หน้ารายละเอียด Incident มีลิงก์ไปหน้า Rollout ที่เกี่ยวข้อง

ใช้ได้ทั้งโหมด `mock` และ `real` เพราะทั้งสองโหมดผ่าน `recordTargetResult()` ตัวเดียวกัน

### 15.6 ตั้งใจยังไม่ทำ

- ส่ง Config ซ้ำเฉพาะเครื่องที่ล้ม (ตอนนี้ต้องสร้าง Rollout ใหม่)

## 16. เวลารอเครื่องที่ไม่ตอบกลับ (Timeout)

### 16.1 ปัญหา

ในโหมด `real` ถ้ากล่องไม่ติดต่อมาเลย (รถจอดนาน กล่องเสีย ไม่มีสัญญาณ) เครื่องนั้นค้าง `pending` ตลอดไป
Rollout ไม่มีวันจบ Auto Pause ไม่ทำงาน และเปิด Rollout ใหม่ให้กลุ่มเดิมไม่ได้ (กลุ่มหนึ่งมี Rollout ค้างได้ทีละรอบ)

### 16.2 ที่มาใน PDF

`GPS_Config_Firmware_Center_Design.pdf` ระบุไว้ระดับหัวข้อ ไม่มีตัวเลข:
- §9.1 Campaign มี Execution: "Batch Size, Concurrency, **Timeout**, Retry Policy"
- §10.1 Pre-check ก่อนอัปเดต: "**Device Online**" (เครื่องออฟไลน์ยังไม่พร้อมรับงาน ไม่ใช่ความล้มเหลว)
- §11.2 กฎอัตโนมัติ: "**Offline หลังอัปเดตเกินเกณฑ์ → Critical Alert** และหยุด Batch ถัดไป"

### 16.3 กติกา

| กรณี | เวลารอ (ค่าเริ่มต้น) | ผลเมื่อครบเวลา | นับเข้า Auto Pause |
|---|---|---|---|
| **ไม่มาดึงงานเลย** (Waiting) | 72 ชั่วโมงหลังปล่อย | `skipped_offline` "ข้าม: เครื่องออฟไลน์" | ไม่นับ (ตาม §10.1 เครื่องออฟไลน์ยังไม่พร้อม ไม่ใช่ Config ผิด) |
| **ดึงไปแล้วเงียบ** (Applying) | 30 นาทีหลัง `pulledAt` | `failed` "ดึงงานแล้วไม่รายงานผลภายใน 30 นาที" | นับ |

- 72 ชั่วโมงครอบคลุมรถที่จอดช่วงสุดสัปดาห์ 30 นาทีเผื่อเวลากล่องใช้ค่า ทั้งสองค่าเป็น**ค่าเริ่มต้น** Operation ปรับได้ตอน
  สร้าง Rollout (ตาม §9.1) และจะยืนยันตัวเลขกับพี่เลี้ยงอีกครั้ง ถ้าพี่เลี้ยงให้ค่าอื่นก็แก้แค่ค่าเริ่มต้น
- `failed` จากการดึงแล้วเงียบผ่าน `recordTargetResult()` ตามปกติ จึงได้ Auto Pause และ Incident ตามหัวข้อ 15
- Incident ที่มีเครื่องดึงแล้วเงียบอย่างน้อย 1 เครื่อง ยกระดับเป็น **`critical`** ตาม §11.2 (กล่องได้ Config ไปแล้วหายเงียบ
  อาจแปลว่า Config ทำให้กล่องใช้งานไม่ได้) ส่วนกรณีอื่นเป็นไปตามหัวข้อ 15.2
- เครื่อง `skipped_offline` นับว่า "มีผลแล้ว" Rollout จึงจบได้ จำนวนที่ถูกข้ามแสดงใน Incident ตอน Rollout จบ ถ้ามี

### 16.4 เครื่องที่กลับมาหลังหมดเวลา

- เครื่อง `skipped_offline` ที่กลับมาออนไลน์ **ยังได้งานนั้น** ถ้า Rollout เป็น `active` หรือ `completed` และเครื่องยังไม่มีงาน
  ใหม่กว่าของ payload ชนิดเดียวกัน (ถ้ามี Rollout ใหม่กว่าหรือ Rollback แล้ว เครื่องจะได้งานของรอบนั้นแทน)
- รายงานผลได้ตามปกติ `skipped_offline` เปลี่ยนเป็น `success` หรือ `failed` พร้อมหมายเหตุ "ล่าช้า" และนับตัวเลขใหม่
  Rollout ที่ `completed` แล้วไม่เปิดใหม่ แค่ตัวเลขถูกต้องขึ้น
- เครื่อง `failed` จากการดึงแล้วเงียบ ถ้ารายงานผลทีหลัง **ไม่เปลี่ยนผล** (ตัดสินไปแล้วและอาจทำให้เกิด Auto Pause ไปแล้ว)
  แต่เก็บข้อความไว้ให้ Operation เห็น

### 16.5 วิธีทำ

- งานตามเวลาทุก 5 นาทีด้วย `@nestjs/schedule` (มีใช้อยู่แล้วกับงานลบ Config อัตโนมัติ) ตรวจเฉพาะ Rollout ที่ `active`
- ไม่ทำงานในโหมด `mock` เพราะ backend apply ให้ทุกเครื่องทันทีอยู่แล้ว
- ทุกคอลัมน์ใหม่เป็น additive ตามหัวข้อ 6
