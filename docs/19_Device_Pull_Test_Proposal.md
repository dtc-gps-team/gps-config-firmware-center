> เอกสารนี้เป็น**ข้อเสนอ ยังไม่ใช่มติ** เขียนให้ kittiphong (B) รีวิวก่อนลงมือทำ ตาม pattern เดียวกับ

>

> แล้วพิสูจน์ว่า Config ที่ปล่อยจากระบบไปถึงเครื่องจริง เครื่องรายงานผลสำเร็จหรือล้มเหลวกลับมาได้
> และหน้าเว็บนับจำนวนถูกต้อง พี่เลี้ยงยืนยันในวันเดียวกันว่าให้ใช้ API key ต่อเครื่องแบบที่มีอยู่ไปก่อน
>
> **ความสัมพันธ์กับเอกสารอื่น:** เอกสารนี้คือการทำ PR 2 และ PR 3 ที่ `docs/14` วางแผนไว้ โดยปรับให้ตรง
> กับระบบปัจจุบัน (Campaign Rollout, ค่าเฉพาะเครื่อง) ส่วน `docs/17` เคยเขียนไว้ว่าเรื่องนี้จะเป็นข้อเสนอ
> ของ B ถ้า B มีร่างอยู่แล้ว รบกวนแจ้งในรีวิว จะได้รวมกันเป็นฉบับเดียว

> เรื่อง Auto Pause แล้วสร้าง Incident อัตโนมัติ ยังไม่อยู่ในเอกสารนี้ จะเขียนแยกหลังจากนี้

## 1. เป้าหมายและขอบเขต

| | ขั้นที่ 1 (เอกสารนี้) | ขั้นที่ 2 (ออกแบบเผื่อไว้ ทำทีหลัง) |
|---|---|---|
| สิ่งที่ส่งเข้าเครื่อง | Config | Firmware |
| เครื่องทำอะไร | ดึงงาน, ใช้ค่า, รายงานผล | ดาวน์โหลดไฟล์, ตรวจ checksum, รายงานผล |
| endpoint | 2 ตัว (หัวข้อ 4) | ใช้ 2 ตัวเดิม เพิ่มชนิดงาน |

**ทำไม Firmware ไว้ขั้นที่ 2:** พี่เลี้ยงขอเรื่อง Config โดยตรง และมือถือติดตั้ง Firmware จริงไม่ได้ จึงพิสูจน์ได้
น้อยกว่า Config มาก แต่ contract ทุกตัวมีชนิดงาน (`payloadType`) ตั้งแต่แรก ขั้นที่ 2 จึงเพิ่มได้โดยไม่ต้อง
รื้อของเดิม ทั้งฝั่ง backend และแอปจำลอง

## 2. ของที่มีอยู่แล้วและจะใช้ต่อ

| ของเดิม | ใช้ทำอะไรในงานนี้ |
|---|---|
| `Device.apiKeyHash` และ `DeviceApiKeyGuard` (#157 PR 1) | ยืนยันตัวตนของเครื่อง ตอนนี้ guard มีแล้วแต่ยังไม่มี endpoint ไหนใช้ |
| ปุ่ม "ออก API Key ใหม่" บนเว็บ | เอา key ไปใส่ในแอปจำลอง |
| `CampaignRolloutTarget` สถานะ `pending` | ใช้เป็น "งานที่รอเครื่องนี้ทำ" ไม่ต้องสร้างตารางงานใหม่ |
| `CampaignRolloutService.recordTargetResult()` | นับ success/failure, Auto Pause, ปิด Rollout เมื่อครบ ใช้ต่อได้ทั้งหมด |
| `mergeApprovedOverride()` | รวมค่าเฉพาะเครื่องที่อนุมัติแล้วเข้ากับ Config ก่อนส่งให้เครื่อง (ตามที่ B ขอไว้ใน #290 ข้อ 6) |
| env `DEVICE_CONFIG_APPLY_MODE` (`mock` / `real`) | ตอนนี้ `real` แค่ throw ว่ายังไม่รองรับ งานนี้ทำให้ `real` ใช้งานได้จริง |

## 3. หลักการ

- **`mock` (ค่าเริ่มต้น ไม่เปลี่ยน):** ทำงานเหมือนเดิมทุกอย่าง ปล่อย Rollout แล้ว backend apply ให้ทุกเครื่องทันที
  เดโมและเทสต์เดิมไม่กระทบ
- **`real`:** ปล่อย Rollout แล้ว backend **ไม่** apply เอง เครื่องเป้าหมายค้างเป็น `pending` จนกว่าเครื่องจะ
  มาดึงงานและรายงานผลเอง
- Auto Pause, Resume, Rollback และการนับผล ใช้กลไกเดิมทั้งหมด
- Rollback ของ Config ในโหมด `real` ทำงานได้เองโดยไม่ต้องแก้: Rollback สร้างเป้าหมายใหม่เป็น `pending`
  เครื่องก็มาดึง Config เก่าไปเหมือนงานปกติ
- Rollback ของ Firmware (สลับพาร์ทิชัน) ยังเป็น mock แยกต่างหาก ไม่อยู่ในขอบเขตนี้

## 4. Endpoint ที่อุปกรณ์เรียก

ยืนยันตัวตนด้วย header `X-Device-Api-Key` ผ่าน `DeviceApiKeyGuard` (ไม่ใช่ JWT เพราะอุปกรณ์ไม่ใช่ผู้ใช้)

**เรื่อง path:** `docs/14` เคยร่างไว้เป็น `GET /devices/{deviceId}/config` แต่ path นี้ถูกใช้แล้วโดย endpoint ของ
staff (`getCurrentConfig` ที่ใช้ JWT) จึงเสนอ prefix ใหม่ `/device-sync/` แยกให้ชัดว่าเป็นของอุปกรณ์

### 4.1 `GET /device-sync/{deviceId}/jobs` ดึงงานที่รออยู่

```json
{
  "serverTime": "2026-10-20T10:00:00Z",
  "pollAfterSeconds": 30,
  "jobs": [
    {
      "jobId": "id ของ CampaignRolloutTarget",
      "rolloutId": "...",
      "createdAt": "2026-10-20T09:58:00Z",
      "payloadType": "Config",
      "config": {
        "configId": "...",
        "name": "GT06N มาตรฐาน",
        "deviceModel": "GT06N",
        "protocol": "TCP",
        "fields": { "SPEED_LIMIT": 180, "APN": "internet" }
      }
    }
  ]
}
```

- คืนเฉพาะงานของ Rollout ที่สถานะ `active` ถ้า Rollout ถูก `paused` จะไม่แจกงานนั้นอีก นี่คือสิ่งที่ทำให้
  Auto Pause หยุดเครื่องที่เหลือได้จริงในโหมด `real`
- `fields` คือค่าหลัง `mergeApprovedOverride()` ค่าที่ sensitive ส่งค่าจริง เพราะเครื่องต้องใช้งาน
- **เรียงตาม `createdAt` จากเก่าไปใหม่ เครื่องต้องทำทีละงานตามลำดับ** งานสุดท้ายคือค่าที่ใช้จริง
  (กรณีเครื่องอยู่ใน 2 Rollout ที่ active พร้อมกัน)
- ไม่มีงาน คืน `"jobs": []` (200) ไม่ใช่ 404
- ครั้งแรกที่งานถูกแจก บันทึก `pulledAt` ที่ target ให้หน้าเว็บแยกได้ว่า "เครื่องยังไม่มาดึง" หรือ "ดึงไปแล้ว รอผล"

### 4.2 `POST /device-sync/{deviceId}/jobs/{jobId}/result` รายงานผล

```json
{ "result": "success", "detail": "ข้อความจากเครื่อง (ไม่บังคับ)" }
```

- `result` เป็น `success` หรือ `failed`
- เรียก `recordTargetResult()` โดยส่ง `rolloutId` ของ job นั้นตรงๆ ไม่เปิด fallback แบบ path ของ Mobile
- **ส่งซ้ำได้ (idempotent):** ถ้า job นั้นมีผลไปแล้ว ตอบ 200 พร้อม `{ "accepted": false }` เพราะมือถือเน็ตหลุดแล้ว
  ส่งซ้ำเป็นเรื่องปกติ ครั้งที่บันทึกผลจริงตอบ `{ "accepted": true }`
- `jobId` ที่ไม่ใช่ของเครื่องนี้ ตอบ 404 (pattern เดียวกับ IDOR Prevention ใน CLAUDE.md)

### 4.3 Online / offline

- ทุกครั้งที่เครื่องเรียก endpoint ข้างบนผ่าน guard อัปเดต `Device.lastSeenAt`
- ถือว่า **online** ถ้าติดต่อมาภายใน 5 นาทีล่าสุด ตอบคำถามเรื่อง online/offline ที่ค้างจากพี่เลี้ยงไปด้วย

### 4.4 ข้อกำหนดของเครื่อง (แอปจำลองต้องทำตาม)

- รอตาม `pollAfterSeconds` เป็นอย่างน้อยก่อนดึงครั้งถัดไป
- ทำงานทีละงานตามลำดับใน `jobs`
- รายงานผลซ้ำได้ถ้าไม่แน่ใจว่าส่งถึง

## 5. Config ปัจจุบันของเครื่องหลังรายงานว่าสำเร็จ (ต้องแก้ก่อนทดสอบ)

ตอนนี้ "Config ปัจจุบันของเครื่อง" (`DeviceService.getBaseConfigForDevice()`) หาจาก **Task ล่าสุดที่ช่างทำเสร็จ**
เท่านั้น ไม่ได้ดูผลของ Rollout เลย ผลคือถ้าเครื่องรายงานว่าสำเร็จ หน้ารายละเอียดอุปกรณ์และหน้าขอแก้ค่าในแอป
ช่างจะยังแสดง Config เดิม ปัญหานี้มีอยู่แล้วในโหมด `mock` ด้วย แต่ไม่เคยเห็นเพราะยังไม่เคยทดสอบครบวงจร

**เสนอ:** Config ปัจจุบัน = รายการที่ใหม่กว่าระหว่าง Task ที่ทำเสร็จล่าสุด กับ Rollout target ที่สำเร็จล่าสุด (Config)
แก้ที่ฟังก์ชันเดียว ไม่เพิ่มคอลัมน์ ไม่เพิ่ม FK

**กระทบ B:** ฟังก์ชันนี้อยู่ในโมดูลของ A แต่แอปช่างใช้ผลของมัน (`GET /devices/{deviceId}/config`) หน้าจอแอปไม่ต้องแก้
แค่จะเห็น Config ที่ถูกต้องขึ้น

  จากเครื่อง และแสดง "ไม่ติดต่อมาเกิน 5 นาที" ที่เครื่องที่เงียบไป

## 8. แอปจำลองกล่อง (B)

อยู่ในส่วนของ B ทั้งหมด A ไม่แตะ

- กรอก URL ของ backend, Device ID และ API key
- ดึงงานตาม `pollAfterSeconds` แสดง Config ที่ได้
- ปุ่ม "สำเร็จ" / "ล้มเหลว" ให้กดเอง และโหมดอัตโนมัติที่ตั้งอัตราล้มเหลวได้ (ใช้ทดสอบ Auto Pause)
- จะเป็นแอปแยก หรือเป็นโหมดหนึ่งในแอปเดิม B ตัดสินใจเอง

## 9. ขั้นที่ 2: Firmware (ออกแบบเผื่อไว้)

- งานใน `jobs` เพิ่มชนิด `"Firmware"`:
  `{ firmwareId, version, fileName, contentType, sizeBytes, checksumSha256, downloadUrl, expiresAt }`
- `downloadUrl` เป็นลิงก์ชั่วคราวจาก MinIO (presigned) backend ไม่ส่งไฟล์ผ่าน endpoint เอง
- **ไม่จำกัดนามสกุลไฟล์** ตามที่พี่เลี้ยงบอกว่าไฟล์ Firmware ตอนนี้มีหลายแบบ ระบบตอนนี้ก็ไม่ได้จำกัดอยู่แล้ว
  เครื่องตรวจความถูกต้องด้วยขนาดไฟล์และ checksum แทน ไม่ดูจากนามสกุล
- คำนวณ checksum ตอนอัปโหลด ไฟล์ที่อัปโหลดก่อนหน้านี้ไม่มี checksum (`null`) ให้เครื่องข้ามการตรวจ
- env `DEVICE_FIRMWARE_APPLY_MODE` (`mock` ค่าเริ่มต้น / `real`) แบบเดียวกับ Config
- รายงานผลใช้ endpoint 4.2 ตัวเดิม

## 10. มือถือเข้าถึง backend อย่างไร และข้อจำกัดที่ยอมรับในการทดสอบ

backend รันบนคอมพิวเตอร์ของ A มือถือเรียก `localhost` ไม่ได้ จึงต้องมี URL ที่ชี้มาหาเครื่องนั้น

**เสนอ: Cloudflare Tunnel (ฟรี) จากเครื่องที่รัน backend** ได้ URL สาธารณะแบบ HTTPS ชั่วคราว
(เช่น `https://xxxx.trycloudflare.com`) เปิดเฉพาะตอนทดสอบ

| เทียบกับ | เหตุผลที่ไม่เลือกตอนนี้ |
|---|---|
| Wi-Fi วงเดียวกัน (`http://192.168.x.x`) | มือถือต้องอยู่ใกล้เครื่อง ใช้ 4G ไม่ได้ Wi-Fi บางที่บล็อกอุปกรณ์ในวงคุยกันเอง และวิ่งแบบไม่เข้ารหัส ใช้เป็นแผนสำรองได้ |
| Deploy ขึ้นคลาวด์ฟรี (Render + Supabase/Neon) | ต้องเขียน Dockerfile ย้ายฐานข้อมูล และเอาโค้ดของบริษัทไปไว้ที่ผู้ให้บริการภายนอก ต้องได้รับอนุญาตจากพี่เลี้ยงก่อน เหมาะกับตอนทำงาน deploy ของ Sprint 4 มากกว่า |

ข้อดีของ tunnel: ไม่ต้อง deploy อะไร, มือถือใช้ 4G ได้, ได้ HTTPS (API key และค่า sensitive ไม่วิ่งแบบไม่เข้ารหัส),
ปิดแล้ว URL หายไป ไม่มีโค้ดหรือข้อมูลไปเก็บที่อื่น

ข้อจำกัดที่ยอมรับ:
- เครื่องที่รัน backend ต้องเปิดอยู่ตลอดการทดสอบ
- URL ฟรีเปลี่ยนทุกครั้งที่เปิด tunnel ใหม่ แอปจำลองจึงต้องให้แก้ URL ได้ (หัวข้อ 8 มีช่องกรอกอยู่แล้ว)
- อยู่หลัง proxy ของ Cloudflare ต้องตั้ง `TRUST_PROXY=1` ตอนเปิด tunnel ไม่งั้น IP ใน Audit Log จะเป็นของ proxy ทุกแถว
  และ**ต้องเอาออกเมื่อปิด tunnel** (ตามข้อห้ามใน CLAUDE.md)
- ใช้ข้อมูลทดสอบเท่านั้น API ของ backend ทั้งหมด (รวม `/auth/login`) เข้าถึงได้จากภายนอกระหว่างที่ tunnel เปิด
- แจ้งพี่เลี้ยงก่อนว่าจะเปิด tunnel ชั่วคราวตอนทดสอบ
- ทุกคำขอต้องตรวจ API key ด้วย bcrypt มือถือ 5 เครื่องทุก 30 วินาทีไม่มีปัญหา แต่ยังไม่มี rate limit ฝั่ง backend

## 11. แผนทดสอบด้วยมือถือ 5 เครื่อง

1. เปิด tunnel ตามหัวข้อ 10 แล้วลงทะเบียนอุปกรณ์ 5 เครื่องบนเว็บ ออก API key กรอกพร้อม URL ของ tunnel ในแอปของแต่ละเครื่อง
2. สร้าง Campaign ที่มี**เฉพาะ 5 เครื่องนี้** (อุปกรณ์ตัวอย่างที่ไม่มีมือถือคู่จะค้าง `pending` ตลอดในโหมด `real`)
3. สร้าง Rollout ด้วย Config ที่อนุมัติแล้ว ให้ 1 เครื่องมีค่าเฉพาะเครื่อง อนุมัติแล้วปล่อย (backend ตั้ง `real`)
4. **ทุกเครื่องสำเร็จ:** เว็บนับได้ 5/5, Rollout เป็น `completed`, เครื่องที่มีค่าเฉพาะเครื่องได้ค่าที่ถูกต้อง และหน้า
   รายละเอียดอุปกรณ์แสดง Config ใหม่ (หัวข้อ 5)
5. **1 เครื่องล้มเหลว:** Auto Pause ทำงาน (เกณฑ์ปัจจุบัน 5% กับ 5 เครื่อง ล้ม 1 เครื่องก็หยุด) เครื่องที่ยังไม่ได้ดึง
   ไม่ได้งานอีก จากนั้นทดสอบ Resume และ Rollback
6. **ปิดเน็ตมือถือ 1 เครื่อง:** เครื่องนั้นเป็น offline ภายใน 5 นาที

## 14. คำถามให้ B ตอบ

1. **Audit Log ของเครื่อง:** `AuditLog.userId` บังคับต้องเป็นผู้ใช้ เสนอว่า**ไม่ลง Audit Log** สำหรับการดึงงานและรายงานผล
   ของเครื่อง เพราะ Audit Log เป็นของการกระทำของคน ส่วนผลของเครื่องเก็บที่ target พร้อมเวลาอยู่แล้ว การกระทำของ
   Operation (อนุมัติ ปล่อย Resume Rollback) ยังลงครบเหมือนเดิม
2. **เครือข่าย:** ใช้ Cloudflare Tunnel จากเครื่องที่รัน backend ตามหัวข้อ 10 โอเคไหม (Wi-Fi วงเดียวกันเป็นแผนสำรอง
   ส่วนการ deploy ขึ้นคลาวด์รอพี่เลี้ยงอนุญาต)
3. ความถี่ในการดึงงาน 30 วินาที และเกณฑ์ offline 5 นาที โอเคไหม
4. ปุ่ม "ยืนยันส่ง Config เข้าเครื่อง" ของช่างในแอป เก็บไว้ใช้คู่กันได้ไหม (เสนอให้เก็บ ไม่กระทบกัน เพราะ
   `recordTargetResult()` กันการนับซ้ำอยู่แล้ว)
5. แอปจำลองจะเป็นแอปแยก หรือโหมดหนึ่งในแอปเดิม
